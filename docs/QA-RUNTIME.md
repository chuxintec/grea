# macOS Unity QA runtime

The `beaver.qa_runtime` module prepares a hash-bound, project-scoped GUI test copy. It does not launch the app during preparation. The parent CLI can expose these functions as:

```text
qa prepare --spec SPEC.json --expected-spec SHA256 [--out FRESH_REPORT_DIR]
qa launch --project ID --build ID --profile ID --expected-owner SHA256 [--duration 60] [--run RUN_ID]
qa collect --project ID --build ID --profile ID --expected-owner SHA256 --run RUN_ID [--out FRESH_REPORT_DIR]
```

Python API:

```python
prepare(spec_path, expected_spec_sha256, out=None)  # out is a fresh directory
launch(project_id, build_id, profile_id, expected_owner_sha256, duration=60, run_id=None)
collect(project_id, build_id, profile_id, expected_owner_sha256, run_id, out=None)  # out is a fresh directory
```

The spec is closed and conforms to `schemas/qa-runtime-spec-1.schema.json`. All IDs are portable stable identifiers. `artifactManifest` is pinned by `artifactManifestSha256`; the existing Beaver artifact manifest is verified with `payload.verify_manifest(..., scope="player", allow_links=True, artifact=True)`. Only its single `player/*.app` is copied. The copy preserves file modes and declared internal symbolic links and does not rewrite signatures. Source and copy signature state/identity are recorded with read-only `codesign` checks; an unsigned source remains explicitly unsigned. Source manifest verification is recorded before and after preparation.

The fixed root is `~/Library/Application Support/beaver/unity-qa/<project>/`. Project ownership binds the stable project ID to the bundle's reverse-DNS `CFBundleIdentifier`; another app cannot silently reuse that project's profile. A project-scoped flock serializes prepares, including the first creation of a project root. App copies are immutable by build ID. Game profile data is at `data/profiles/<profile>` and shared across builds; a matching stable owner record lives outside that directory at `data/profile-owners/<profile>.json` so clearing a QA profile does not remove its ownership identity. `profileSeed` is either `null` (a new empty QA profile) or a complete hash-pinned Beaver manifest inventory copied with its relative paths only when a profile is first created. Later runs and builds preserve runtime edits. Explicit `configInputs` are copied by content hash to `data/configs/<build>/<id>.json`, so sensitive configuration does not enter the app bundle. Process receipts, logs, temporary files, and locks are held separately under `data/runs`, `data/logs`, `data/tmp`, and `data/locks`; app-managed profile clearing cannot remove them. Final control files use exclusive/no-follow creation or no-follow updates, and all path components including dangling symlinks are rejected. Each copied input records source hashes before, during, and after copying. Unowned roots, symbolic-link roots, owner-record drift, existing build IDs, and later source edits are rejected. A prepare receipt records staging roots and commit progress for recovery review. Optional `--out` values are fresh directories containing `qa-prepare.json` or `qa-collect.json`; durable copies remain under Data receipts.

Environment values are generated only from typed `environmentBindings`: a declared config ID becomes its controlled Data file path, and a profile binding becomes the owned profile root. At least one explicit profile binding is required. Arbitrary environment values and external runtime paths are not accepted; reserved runtime/control variables are rejected. The default environment is a small allowlist and retains the real user `HOME`; `TMPDIR` is controlled Data. `arguments` is an ordered list of literal tokens from a limited screen/diagnostic set. `-logFile` is generated internally. No shell is used, and paths, control characters, shell syntax, batch/headless modes and arbitrary process options are rejected. Parent CLI integration should reject unsupported tokens before calling the module.

`launch` is an explicit operation, starts the bundle executable directly as a GUI app, writes Unity and console logs under controlled Data, and waits within a bounded duration. A profile lock outside the game data prevents concurrent use of the same QA profile. A budget timeout sends a graceful terminate only to the process created by this call. It never sends SIGKILL. Such a result is `stopped_by_budget`, not a normal application exit; an unresponsive child remains recorded as recovery-required. Non-zero exits are failed with their code preserved. No automatic UI or privacy prompt response is attempted. `denyDocuments` adds a closed macOS `sandbox-exec` profile denying read/write beneath the resolved Documents directory; receipts record that the restriction was requested and whether launch completed, not that enforcement or lack of file access was independently proved. It does not alter TCC and does not establish that TCC was clean. Unsupported/removed `sandbox-exec` platforms may fail to launch.

`collect` requires an explicit `runId`, strictly matches project/build/profile ownership, and includes only the exact Data log derived from that run and profile. It produces a separate report with owner, source/artifact identity, bundle hash, process receipt and log hashes; bundle drift makes collection failed. Launch returns its process receipt as `report`, including exact command, cwd, clean typed environment paths, executable SHA256, and expected owner SHA256, without config contents. An exited receipt preserves the exit code without relying on a possibly reused PID. A running receipt is reported as verified-running only if Darwin's process executable path, unchanged process start-time value, and this run's log argument match; otherwise presence is identity-unknown. It does not claim syscall-level file-access evidence. A denied Documents access during the closed test mode can support path investigation; runtime access provenance otherwise must be supplied by the consuming project's authorized evidence workflow. Debug strings or source paths alone do not prove a runtime file access. At least one declared profile binding is required, but the consuming app must actually use it for QA save isolation; `HOME`, Unity `persistentDataPath`, PlayerPrefs and ordinary AppData are not redirected or claimed isolated. GUI startup, login/menu reachability, normal exit, reopen/save-resume, visual parity and gameplay acceptance remain distinct consumer checks.

The module does not launch Unity/Player itself while preparing, change TCC, sign or notarize the app, install tools globally, or grant access to production/ordinary player data. Callers must supply only explicitly authorized test inputs and verify that the application consumes the profile binding. Its tests use a temporary mock home and fixture bundles; they never execute a fixture process.

Seed file bytes are compared with the pinned inventory during copying and the source seed is reverified afterward. Preparation fails before promotion if a seed changes after its initial scan. Unity `-logFile` and redirected stdout use separate files; collection binds both exact paths to the run identity.

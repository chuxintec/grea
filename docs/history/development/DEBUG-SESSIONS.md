# Fixed candidate debug sessions

## Optional project observation and external deadline

The existing `debug start` accepts optional `--observation-spec SPEC --expected-observation SHA256` and `--deadline-utc YYYY-MM-DDTHH:MM:SSZ`. The original call remains valid. This is the same owned worker and process lifecycle, with no input dispatch or arbitrary command/environment passthrough.

The [closed observation schema](../../../schemas/development/debug-observation-1.schema.json) describes only one project-owned observation-root argument and an optional exact bundle precondition:

```json
{"schemaVersion":1,"contract":"beaver-debug-observation/1","rootArgument":"-sampleEvidenceRoot","expectedBundleIdentifier":"com.example.neutral"}
```

The argument must be an observation/evidence-root name allowed by the schema. Its value is generated from the newly created `--out` session directory; the spec cannot select another path. The original spec bytes are SHA-bound and copied into the session. The worker rechecks the snapshot and full artifact before launch. An optional `expectedBundleIdentifier` is compared with the manifest-bound app's actual `Info.plist`. No raw argv, environment, executable, profile reset, gameplay callback or input backend can be supplied by this spec.

Observation-enabled sessions start in the app bundle root. Their project observer must be explicitly opt-in and must treat the supplied path only as a new evidence destination. The observer and any business assertions remain project code. `player.log` is Unity's generated `-logFile`; `console.log` captures process stdout/stderr, and `worker.log` records worker diagnostics. The worker records the literal arguments and `launchCwd`. Preparation and lifecycle evidence do not authenticate observer screenshots, visual parity or gameplay.

The effective deadline is the earlier of the duration budget (1–3600 seconds) and the explicit external UTC deadline. Past or malformed deadlines are refused; expiration during preparation or the async handoff starts no candidate. Once running, expiration uses the existing worker-owned termination sequence and records `stopReason` as `external_deadline_expired` or `duration_budget_expired`; the existing failed-budget status is preserved. An observation-enabled session also accepts a `STOP` file inside that same output directory. `debug stop --session ...` remains the normal public stop operation and never signals a caller-supplied PID.

Only the worker's own `Popen` child can be terminated/killed/waited. Caught failure paths perform the same cleanup. Final status includes `exitCode`, `exitedUtc`, `childReaped` and post-run artifact verification. `childReaped` states only that this `Popen` was waited/reaped; independent PID absence is separate, as are normal exit, requested stop, budget stop and business acceptance. A new invocation with a fresh output directory cold-starts a new process; there is no automatic restart or removal/reset of a QA profile. Existing `qa prepare/launch/collect` contracts and typed profile/config bindings are unchanged.

`beaver.debug.start(manifest, output, expected, duration=3600, width=None, height=None)` starts a detached worker for one fixed, hash-verified macOS `.app` candidate. `duration` is required to be an integer from 1 to 3600 seconds. Width and height are optional as a pair; each must be an integer from 64 to 8192. With neither supplied, the candidate follows its own PlayerSettings. The session records `requestedViewport`; worker status records the actual `launchArguments` passed to the app. A requested viewport does not establish the resulting window size, DPI scaling, or rendered dimensions. The three-argument call remains valid and uses the one-hour ceiling. The worker owns the candidate process after the invoking CLI exits, watches its real exit code, and requests termination at the deadline. `inspect_session(session)`, `stop(session)`, `tail(session, lines=80)`, and `screenshot_record(session, path, expected_sha)` accept the `session.json` path or the start result.

The artifact manifest must be pinned by its explicit SHA-256 and pass `payload.verify_manifest` before launch. The app executable path and hash must belong to that manifest. A per-session UUID is added as a command-line marker; status records bind PID, marker, executable path/hash, and process start time. The immutable `session.json`, atomic `status.json`, separate stop request, and append-only screenshot evidence files avoid concurrent read-modify-write loss. A successful `ps` result with no PID is `exited`; probe errors, denied access, or incomplete identity fields are `identity_unknown`. External inspection never signals an unverified PID. The detached worker manages only its own `Popen` child, processes stop requests through that handle, and applies the bounded termination sequence at the deadline. There is no automatic restart.

Statuses describe process lifecycle: `starting`, `running`, `stopping`, `stopped`, `exited`, `failed`, or `identity_unknown`. Exit code zero means the process exited normally; it does not establish gameplay success. This API launches an app candidate (`kind=App`). It does not attach to a Unity Editor or infer PlayMode from editor capability. Any separate Editor/PlayMode observation must remain read-only and report the observed kind and evidence source.

The worker receives only basic launch environment entries and does not receive stale `BEAVER_*`/`MONKEY_JOB*` control variables. Logs are file-backed, never streamed to CLI output. `tail` seeks to the end and reads at most the final 256 KiB before line and credential redaction, independent of total log size. Screenshot evidence is caller-supplied: its explicit SHA-256 is checked and its source is recorded as unverified caller input. An `actualScreen` measurement must come from screenshot or application-result evidence; a requested viewport is not that measurement. The module does not capture, synthesize, or authenticate screenshots. Sessions are limited to the fixed candidate and are intended for isolated artifacts, not real ExampleGame, backend services, or player saves.

`inspect_native(transaction)` is a separate read-only inspector for v1 Unity and v2 batch transaction directories. It checks plan/journal hashes and project identity against the recorded native report, reports the persisted process PID/ownership/exit fields and available log/evidence paths, and never attaches to or signals an Editor. A recorded live process is reported as `process state unverified`; it is not proof of a current connection. Unity v1 `process.json` does not store the Editor executable path, so that result is explicitly partial. A `validate.play` plan is only `observedPlayMode` when its matching native report records positive `playFrames`; otherwise it remains planned and unverified. Even observed frames do not establish a GUI screenshot or interactive gameplay verdict.

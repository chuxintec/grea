# 设计依据与证据边界

本次采用源码、项目开发记录和已保存报告的只读核对。完整来源清单见 [evidence.json](evidence.json)，包含 99 个文件的匿名编号、完整 SHA-256、字节数与用途，以及 31 项结论到来源的映射。

这不是本轮重新运行的 Unity/Player 验收报告。公开源报告原件不随 grea 分发，外部读者不能仅凭摘要独立复现这些私有样本结果；hash 用于确认持有原件者核对的是同一份材料，不能代替原件或执行证据。

## 如何读证据

- `Sxx`：项目材料。原路径、项目身份和逐文件冻结副本保留在本地忽略目录；公开文件只保留用途和 hash。
- `Rxx`：第二次复评的当前源码、报告与只读盘点；本地映射与首轮S编号分开。
- `Gxx`：公开 grea 源码，机器索引提供仓库相对路径。
- `Exx`：本轮观察/结论；方法区分 `source-inspected`、`documents-read`、`source-and-records-read`。
- `Kxx`、`Txx`：待整合规范/工具工作项，不是已执行能力。
- `examples/`：新编的合成示例；没有原版 hash，不为实测提供证明。

**首轮历史边界（draft.1）：** 读取期间源工程仍在更新。初始指纹与证据冻结之间，计划、待验清单和一个组合源码有变化，已另存前后身份并复核相关内容。**文件快照不等于同一次原子捕获的可构建整工程**；本提案不据此创建或认证 Player。新增摘要中提及正在进行的真实回归，其关联报告在读取时尚未落盘，因此没有把这部分状态升级为本次已核验运行结果。后续开发必须重新固定完整输入。

## 本地追溯与后续更新

维护者的本地设计证据目录保存：初始输入清单、逐文件副本、原路径/副本/hash映射，以及收尾时的源漂移检查。它是本任务证据，不是新的 memory 后端，也不是项目运行依赖。原始游戏证据仍以源项目为准。

复核步骤：从 Exx 取得 sourceIds → 在本地映射中定位原件/副本 → 计算完整SHA-256核对 → 读取对应构建/测试身份和否定字段 → 再判断某项方法能否提升为规范。源工程继续变化时新增设计版本和证据身份，不覆盖旧报告后沿用原通过结论。

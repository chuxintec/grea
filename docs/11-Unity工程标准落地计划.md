# Unity 工程标准 v1 落地计划

日期：2026-10-13。设计基线为 [Unity 工程标准 v1](../skill/references/20-标准工程目录与类型归类.md)，规范版本 `1.0.0`。本文件只维护工作分解、依赖、验收与状态；目录、组件和生成契约由标准正文维护。

当前分支：`codex/unity-engineering-standard-v1`，起点为 `v2026.10.13-rc2` 的提交 `91548fb`。当前授权仅覆盖制定规范与计划、文档路由和必要验证；**不开发框架/生成器、不创建 Unity 工程、不安装依赖、不修改现有游戏工程**。本轮不升级产品版本、移动发布标签或修改已发布制品。

## 1. 当前能力与缺口

| 事项 | 当前可复用能力 | 仍需实现/验证 |
| --- | --- | --- |
| 资产身份 | unity_asset_ledger 的 snapshot/compare/check-plan/verify-moves | 工程生成所有权、模板版本、字段/对象级生成清单 |
| 静态依赖 | unity_dependency_audit 文本 GUID 闭包 | 程序集方向、配置语义、动态寻址和完整 Editor 回读 |
| Editor 审计 | RecoveryRuntimeAudit.cs 的现有只读检查 | 标准 Prefab 绑定契约、场景/服务所有权验证 |
| 流程一致性 | 轨迹差分、现有 CLI/MCP 受控执行与回执 | Unity 框架生命周期、取消、池化和存档专项测试 |
| 规范 | 既有资产治理、UI 迁移、构建与分层验收 | 本次补齐工程标准；实现证据仍为空 |
| 工程生成 | 尚无已注册的工程生成操作 | profile、计划/执行、可恢复 Editor 生成器和验证器 |
| 通用资产 | 包备份工具与运行时构建辅助源码 | 自有公共框架包、通用 Prefab、最小参考工程 |

现有通用 Python 回归、帮助调用或已发布 rc2 不作为未来 Unity 框架的运行证据。新工具不可沿用现有工具 ID 冒充不同语义；兼容 ID 与已有工作流保持稳定。

## 2. 首版交付范围

目标是让维护者基于一份锁定配置，在干净目录生成一个可运行的参考闭环，并能安全重复生成和定位失败。完整闭环为：启动→主界面→进入最小玩法→暂停/恢复→返回→再次进入→关闭重开；使用自有几何、合成配置和明确可分发资源。

首版仅提供一组实际验证的 Unity 精确版本、URP/uGUI、输入方案与 macOS Player 组合。Unity 6 的具体补丁版本、包版本、架构和脚本后端在 M1 开工时根据已有环境锁定，写入矩阵；选定之前不填“支持 Unity 6 全版本”。初版资源后端使用序列化引用/显式 Catalog，资源端口保留替换能力。已有项目的 Resources、Addressables、AssetBundle、UI Toolkit 与第三方 UI 只定义适配边界，不在首版自动转换。

首批组件限作用域/初始化、页面/弹窗、基础输入反馈、资源句柄、音频句柄、最小存档适配与诊断。复杂虚拟列表、通用战斗框架、全局消息总线、ECS、联网、热更新、商业 SDK 和多平台全量适配不进入首版承诺；当试点确实需要时再单列范围。

## 3. 实施顺序与门槛

M0 为本次文档工作；M1–M5 为后续待授权实施。阶段依赖是 M0 → M1 → M2 → M3 → M4 → M5，不按“文件已经建立”计算完成。每阶段关闭门槛后再推进；新失败只重验受影响范围，不能以重复跑无关测试填补缺口。

| 阶段 | 输入与工作 | 交付物 | 退出条件 | 当前状态 |
| --- | --- | --- | --- | --- |
| M0 规范与计划 | 审查既有规范、确定默认/例外/未实现边界 | 标准 v1、计划、导航、维护场景 | 链接/锚点/技能检查通过，前向场景走查无范围扩大；改动限文档 | 文档已完成，维护检查通过 |
| M1 配置与静态规划 | M0；确定精确工具链与参考组合 | profile/plan/manifest/report schema、校验器、只读计划能力 | 有效/无效/越界/组合不支持等夹具通过；计划不写目标；现有 ID/契约不漂移 | 未开始 |
| M2 最小框架与包 | M1 契约；可用且获准的 Unity 环境 | 最小 foundation、必要 UI 组件、Editor 包及包测试 | asmdef 依赖无环；初始化/失败清理/绑定重入通过；包能独立安装和编译 | 未开始 |
| M3 生成器与 Prefab | M2；标准模板和所有权协议 | Editor 生成/绑定/校验、受控执行、清单与恢复 | 重复生成无漂移；人工改动不丢；中断后可识别/恢复；所有拟议 API 有实际实现 | 未开始 |
| M4 参考闭环与分发 | M3；干净参考目录与锁定依赖 | 自有参考工程、自动化/手动验收、包分发说明 | A0–A4 对所选组合通过；解包/独立恢复/重复生成与 Player 闭环均可复现 | 未开始 |
| M5 隔离试点与推广 | M4；两个业务结构不同且获准的试点 | 模块迁移差异、例外、回归与升级/回退说明 | 两个试点受影响范围 A5 通过，公共组件与项目特例边界稳定，再决定推广 | 未开始；不得操作现有工程 |

M2 内纯契约设计可先于 Unity 原生测试完成，但不能提前标记阶段通过。平台或编辑器不可用时记录 blocked/not_run，继续不依赖它的文档/静态工作，不伪造 Unity 验证。开发可以由同一维护者完成；本计划不授予启动子 Agent 或并行修改同一 Unity 工程的权限。

### M1 工作分解

1. 冻结 profile 字段与 schema 版本；区分必填、默认、可选，以及 new/adopt/refactor 模式的不同前置条件。
2. 定义计划项和生成清单的逻辑 ID、路径/内容/meta 身份、所有权、输入过期判断与错误分类；清单路径相对项目根。
3. 定义能力矩阵，实际核对编辑器、包和平台模块，记录证据等级。安装、许可、登录和外部获取遵循实际授权。
4. 实现静态校验和只读计划，复用现有资产台账/依赖工具的适用部分。不能把文本扫描结果声明为 AssetDatabase 的实际导入类型。
5. 为 schema 与规划建立合成夹具：空目标、已存在工程、中文/空格路径、同名不同大小写、符号链接越界、未识别字段、未知模板/模块、资源冲突和依赖缺失。
6. 公共接口只在实现就绪时加入 contracts.py 和 registry；由现有生成脚本维护 schemas，并验证 CLI/MCP 同源结果和失败回执。

M1 输出的配置和计划必须能独立审阅；除规定的新报告外，目标工程字节与文件数不变。不能预建空 Runtime/Prefab 树来声称已完成生成能力。

### M2 工作分解

1. 实现纯 Contracts 与最小运行作用域；定义初始化顺序、重复调用、失败逆序清理、任务取消和代次检查。
2. 建立 Game.Domain / Gameplay / Presentation / Services / Bootstrap 的最小参考装配；UI 不直接修改持久化状态。
3. 实现首批组件及契约文档，优先覆盖弹窗二次打开、一次点击两次请求、切关晚回调和音频遗留等可观察问题。
4. 增加资源/存档/平台端口与简单实现；不引入不需要的万能抽象。存档测试使用合成数据与独立 QA 位置，原格式适配留试点阶段。
5. 按实际包内容维护 package.json、asmdef、meta、许可证、依赖锁和测试。基础包不得依赖 Game 或 Editor 程序集。
6. 每个组件给出最小用例和至少一个失败用例；把初始模板骨架与公共运行代码明确分开。

M2 不承诺完整项目转换，也不把“框架包能编译”写成“游戏能恢复”。

### M3 工作分解

1. 先实现只生成小型新工程的路径，再实现已有工程的只读 adopt；refactor 写入能力待明确支持的操作和试点范围齐备后开放。
2. 固定模板包含的文件所有权：seed-once、generated、human、package；标明扩展点与禁止覆盖区域。
3. 经 Editor API 创建配置、Bootstrap 场景、UIHost/ModalShell 等已实现 Prefab；记录 GUID、必要 fileID 和绑定回读。
4. 将 Unity 长任务交给既有连接与受控执行层；补充等待编译/重载、超时核查、输出预算和执行中断状态，避免重复提交。
5. 实现输入重检、冲突报告、前像与恢复日志；测试每个可能留部分输出的阶段。恢复只作用于本次清单，不覆盖后来的人工作业。
6. 校验 Prefab 必需字段、同名类型冲突、Variant 覆盖、初始化唯一性和程序集方向。校验发现问题默认不自动改资产。
7. 加入 UI 技术栈/版本不匹配、生成清单缺失、模板升级、旧生成器恢复请求等失败案例；不靠删除 Assets/Library 处理冲突。

### M4 工作分解

1. 用已锁定模板在独立目录生成参考工程；素材全部可分发，不引入原包、私人插件或开发机 .private 文件。
2. 完成最小玩法闭环与日志关联；测试初始化失败、重复进入、暂停/恢复、退出时取消、配置错误和存档关闭重开。
3. 先运行静态和 EditMode，再 PlayMode，再所选目标 Player。分别保留真实执行、退出码、版本、场景、断言和未执行项。
4. 从分发包在新的目录恢复依赖并运行；确认没有工程外路径、软链接和开发机缓存的隐式依赖。验证同一工程重复生成稳定及不同路径的结构等价。
5. 检查包体、许可证、meta/GUID 与测试资源剔除；把精确已验组合写入能力矩阵，未测组合保持未验证。
6. 更新安装/升级/回退文档和实际工具目录，再决定独立框架包版本及 grea 发布版本；不复用或移动既有 rc 标签。

### M5 工作分解

1. 明确两类获准试点及所迁模块，例如以界面导航为主和以多实体会话为主的不同结构；不预先指定或占用现有游戏项目。
2. 从隔离副本记录目录、程序集、资源、动态键、存档和行为基线。第一轮只 adopt 与差异计划；正式写入沿用当前明确授权范围。
3. 一次迁移一个可独立回归的模块；公共组件只抽取已证明通用的契约，项目特例通过端口留在项目。
4. 回归原规则、随机消费、关键时序、真实输入、视觉/音频及关闭重开；需要性能目标时先冻结设备、负载和预算，再对比。
5. 记录成本与结果：首次可运行耗时、手工修复项、重复生成差异、定位失败所需步骤、回归缺陷和例外。基线未知时不声称提高某个百分比。
6. 两个试点通过后评审稳定契约、必要扩展和删除候选；不凭单个参考工程的成功批量迁移工作区。

## 5. 验收与失败路径跟踪

标准中的规则 ID 用于计划项、检查结果和例外关联。自动化只能证明其实际执行的层级，不能用规则关键词匹配替代运行判定。

| 标准规则 | 首个负责阶段 | 必须覆盖的验收 |
| --- | --- | --- |
| STR-01–04 | M1/M4 | 目录职责、缺省/例外、无空壳、独立恢复、无工程外路径依赖 |
| ARC-01–03 | M2 | 编译引用方向、无循环、Runtime 不引用 Editor/Tests、依赖装配可追踪 |
| LIF-01–04、DAT-01–03 | M2/M4 | 失败清理、Play 重入/静态重置、取消晚回调、时钟/RNG、配置/状态/存档隔离 |
| CMP-01–03 | M2/M5 | 组件契约、失败样例、有界诊断及异结构复用 |
| PFB-01–04 | M3/M4 | 字段/插槽绑定、Variant、生成覆盖、真实显示与关闭重入 |
| SCR-01–03 | M2/M3 | 人工/再生代码隔离、角色职责、线程/异步/序列化与 AOT 风险 |
| GEN-01–05 | M1/M3 | 重复生成、stale_plan、权限/路径范围、并发、冲突、恢复和错误回执 |
| ACC-01、UPG-01–03 | M4/M5 | 分层状态真实、版本矩阵、显式升级、行为差异与例外有效性 |

每份验收报告至少包含：规范/profile/模板/生成器/包版本与哈希、源码和 buildId、Unity/平台/架构/后端、项目与模块范围、规则 ID、输入身份、预期和实际、pass/fail/not_run/blocked/not_applicable、证据引用、未解决项。禁止提前生成虚构通过记录。

Python 静态与协议验证可复用当前 Source checks；Unity EditMode/PlayMode 和 Player 验证需要获准的编辑器、许可和平台 Runner。实施前先确认资源，再增加 CI 作业；不能因为现有 GitHub ubuntu 工作流通过就声称 Unity 已测。托管 Runner 不预装私人依赖，许可/凭据不进入模板或日志。

## 6. 主要风险与处置

| 风险 | 早期信号 | 处置与停止条件 |
| --- | --- | --- |
| 过度框架化 | 大量未引用接口、空目录、单用途“通用”组件 | 回到参考闭环；删除未被需求驱动的设计，特例留项目 |
| 生成覆盖人工修改 | 清单无法判断所有权、模板替换整份 Prefab | M3 先做冲突与恢复；未证明保留能力前不开放已有工程写入 |
| 原版语义变化 | 时钟/RNG/存档/回调顺序被统一模板重写 | 停止相应迁移，恢复基线，通过适配和差分重验 |
| 编辑器版本漂移 | 同模板在不同机器导入结果变化 | 锁定版本矩阵与依赖哈希；不以最新版替换原组合 |
| UI/资源方案耦合 | 基础包引入 uGUI、Spine 或 Addressables 特定类型 | 移至可选适配包；缺实现明确不支持，不静默替代 |
| 虚假的“幂等” | 文件未变但重复节点、监听或任务不断增加 | 同时验证资产身份、运行对象和生命周期，不能只比较文本 |
| 打包泄漏或不自包含 | 包内含项目素材/本机路径，缺失开发机即失败 | 分发扫描与全新副本恢复；未通过不发布 |
| 验收层级混淆 | 帮助/编译/Editor 测试被写成真实游戏通过 | 报告字段分层，保留 not_run，按实际范围收口 |

## 7. 当前交付与后续启动条件

本轮交付：标准正文、该落地计划、README/技能入口及现有参考的导航更新、维护场景补充和文档检查。工作区既有游戏工程、框架源码、模板、Prefab、正式 API/schema 与已发布版本均不修改。

后续启动 M1 时落实以下选择：精确工具链与首个能力矩阵条目、可用 Unity/构建环境、最小参考闭环模块、依赖分发来源和测试证据位置。能从当前环境与既有授权确定的事项直接核对，不重复询问；会改变平台、玩法、外部安装或现有工程范围的选择再明确。

标准 v1 的文档完成不等于 M1–M5 已实施。本计划的阶段状态只能随真实产物和验收更新；发布一个 grea 版本不会自动把这些阶段升级为完成。

本轮维护检查和场景走查记录见 [规范验证摘要](validation/2026-10-13-unity-standard-v1.json)。该记录只验证文档、链接和维护决策，不是框架或 Unity 工程的实测记录。

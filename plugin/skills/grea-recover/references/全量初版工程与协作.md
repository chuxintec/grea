# 全量初版工程与协作

## 恢复流程

完整恢复／首次重建依次完成：来源冻结 → monkey 全量导出独立候选 → GREA 核来源去向和交接 → beaver 在隔离工程采用并做适用的原生验证 → 游戏 Agent 在[开发阶段](../../grea-develop/SKILL.md)接续业务。只读研究、来源辨识和输入准备可以先行；已有可维护工程的局部修复不强制重新导出。

monkey 负责源格式解析、资源转换、目标资产装配及代码依据/初稿；源格式转换缺口归 monkey。GREA 负责工作流、来源冻结、规范入口和交接判定；beaver 负责开发工程的采用、编辑及验证工具；工程操作缺口归 beaver；游戏 Agent 负责产品业务，产品代码与证据仍留游戏项目。GREA 不另写转换器，monkey 不代做整套游戏业务。Unity 来源的 Unity 目标和 Creator 来源的 Unity/Creator 目标，均以本次声明及固定 provider 的实际支持为准；不支持的目标明确保留为缺口。

## 冻结输入与候选范围

输入清单按游戏、来源引擎/版本和修订冻结，登记主包、分包、Bundle、代码/metadata 及有证据支持的补齐文件。全量只表示这份明确的来源集合，不承诺未知服务器数据、未取得的远端内容或所有受保护代码。原件只读，工具版本、能力与计划身份固定，既有计划不随 provider 新版本切换。

每项输入都要有处置和去向；每个逻辑资产都要保留唯一来源 ID 到目标路径/GUID 的映射。候选应含适用的资源、Scene/Prefab、动画、字体/音频、配置及可恢复代码依据。未恢复的方法、资源和不支持项保留来源位置、证据、原因或 TODO，并与已确认实现区分。空类、lookup、IR、gallery、媒体池、文件数量或 `conversion.completed` 都不能冒充完整初版。

## 初版交接门

先由 monkey 生成独立候选，再依据 manifest 和实际产物核每项输入的去向、哈希、引用和未完成项。源类别决定检查内容：源有 Scene/Prefab 时核对实际原生图文件与引用；没有该类别时不凭空设数量门。候选的文件完整性与工程可导入/编译分别验证；适用时使用真实目标引擎回执。静态字节、`completed`、目录规范、provider 可用和 exit 0 不能单独放行。

批量恢复的工具 ID、精确调用、版本绑定、预算、输入 Schema 和旧接口边界由共享的[monkey 恢复工具合同](../../grea/references/monkey恢复工具合同.md)维护。GREA 用 `monkey_pipeline` 做计划、执行和文件审计；需确认来源到原生资产去向时再使用显式 handoff 合同。具体调用前读[monkey/beaver 调用规范](../../grea/references/monkey与beaver调用.md)核两个 provider 的固定身份与权限。这里不复制参数表或安装步骤。

## 开发接续

只有来源、候选与适用原生交接证据核清后，才由 beaver 在隔离工程采用/比较候选，由游戏 Agent 接续规则、界面、交互、服务和存档。已有工作工程参与比较/合并时，按来源身份保护既有代码、GUID、正式 JSON 和存档。此交接不是完整可玩验收；业务、视觉、真实输入、存档续玩和目标平台按开发阶段及本期范围另行验证。若交接不完整，保留缺口并停在恢复阶段，不以小样替代全量候选。

# 全量初版工程与协作

## 恢复流程

完整恢复／首次重建依次完成：来源冻结 → monkey 全量导出独立候选 → GREA 核来源去向和交接 → beaver 在隔离工程采用并做适用的原生验证 → 游戏 Agent 在[开发阶段](../../grea-develop/SKILL.md)接续业务。只读研究、来源辨识和输入准备可以先行；已有可维护工程的局部修复不强制重新导出。

monkey 负责源格式解析、资源转换、目标资产装配及代码依据/初稿；源格式转换缺口归 monkey。GREA 负责工作流、来源冻结、规范入口和交接判定；beaver 负责开发工程的采用、编辑及验证工具；工程操作缺口归 beaver；游戏 Agent 负责产品业务，产品代码与证据仍留游戏项目。GREA 不另写转换器，monkey 不代做整套游戏业务。Unity 来源的 Unity 目标和 Creator 来源的 Unity/Creator 目标，均以本次声明及固定 provider 的实际支持为准；不支持的目标明确保留为缺口。

## 冻结输入与候选范围

输入清单按游戏、来源引擎/版本和修订冻结，登记主包、分包、Bundle、代码/metadata 及有证据支持的补齐文件。全量只表示这份明确的来源集合，不承诺未知服务器数据、未取得的远端内容或所有受保护代码。原件只读，工具版本、能力与计划身份固定，既有计划不随 provider 新版本切换。

每项输入都要有处置和去向；每个逻辑资产都要保留唯一来源 ID 到目标路径/GUID 的映射。候选应含适用的资源、Scene/Prefab、动画、字体/音频、配置及可恢复代码依据。未恢复的方法、资源和不支持项保留来源位置、证据、原因或 TODO，并与已确认实现区分。空类、lookup、IR、gallery、媒体池、文件数量或 `conversion.completed` 都不能冒充完整初版。

## 初版交接门

先由 monkey 生成独立候选，再依据 manifest 和实际产物核每项输入的去向、哈希、引用和未完成项。源类别决定检查内容：源有 Scene/Prefab 时核对实际原生图文件与引用；没有该类别时不凭空设数量门。候选的文件完整性与工程可导入/编译分别验证；适用时使用真实目标引擎回执。静态字节、`completed`、目录规范、provider 可用和 exit 0 不能单独放行。

批量恢复的工具 ID、精确调用、版本绑定、预算、输入 Schema 和旧接口边界由共享的[monkey 恢复工具合同](../../grea/references/monkey恢复工具合同.md)维护。GREA 用 `monkey_pipeline` 做计划、执行和文件审计；需确认来源到原生资产去向时再使用显式 handoff 合同。具体调用前读[monkey/beaver 调用规范](../../grea/references/monkey与beaver调用.md)核两个 provider 的固定身份与权限。这里不复制参数表或安装步骤。

## Prefab完整恢复的独立对照

从原包恢复Prefab时，先冻结原包/版本/hash、源UUID/RF/class/node身份及资源/代码闭包。项目中现有的导出文件或修补版只用于定位与差异线索，不能当作原包真值。分开保存：原包及匹配版本的原版状态、旧工具纯输出、新工具纯输出、游戏人工修补结果；纯输出不得调用游戏Author/Repair/Integrate补丁补节点、改布局或补业务方法后归功于恢复器。允许独立最小宿主与有来源的状态输入，但不让夹具修改被验Prefab或暗补功能。

### 源组件分母与映射

按每个源节点/序列化组件建立账本，记录字段、引用、事件及预期依据，再分别核“源→IR是否遗漏”和“IR→目标是否正确”。未知/忽略/不支持的源组件仍进入分母，不能只检查生成器自己的计划。原生零MissingScript、文件/节点数量或编译通过不证明组件覆盖。动态生成对象另记源码依据及状态，不能混入静态组件数制造覆盖率。

| 账本层 | 必须保留的事实 |
| --- | --- |
| 源 | 固定来源身份、组件/序列化版本、字段与别名、对象引用/事件、解码状态；不可读部分明确未知 |
| 映射 | 目标资产/对象/类型/属性及恢复规则、缺口；一对多/多对一说明原生表达与语义依据 |
| 验证 | 静态/导入/保存独立重开/挂载/动态/视觉/输入分别记录结果和候选身份 |

跨版本/跨引擎完整恢复指明确范围内的显示、引用和行为等价，不要求目标字节或组件名称相等；使用目标原生机制，不嵌入源引擎解释器。源未支持项不能丢弃、塞空壳或擅自排除分母。最终分别报告源组件总量、已映射/未映射及字段/引用/事件完整性，支持率不冒充完整恢复率。账本是证据要求，不是尚未交付的CLI或Schema；账本和源数据分析用于核对并定位真实失败，恢复本身仍按[成组Prefab恢复与采用](成组Prefab恢复与采用.md)由 monkey 程序完成。

### 先静态完整，再动态恢复

第一阶段逐目标、逐样本核七项：来源身份、父子层级、组件与序列化字段、图片/文字/材质等资源引用、真实图形后端的静态渲染、保存后独立重开、同输入再生。保留pivot/裁切/九宫格、字体/描边、遮罩/排序和属性别名；源→IR与IR→目标分别检查。七项满足本次批准范围时可记 `staticAcceptance=pass`，不等待完整业务脚本或物理输入。

业务行为可标 `disabled/not_run/partial`。允许按来源声明生成可序列化类型、字段及引用载体以保全组件，但无字段空壳不能冒充静态完整，空回调不算行为恢复。必要的原生布局求值可执行，业务、网络、奖励等按本次范围禁用。静态排序代理须声明其绘制状态与可更新边界；静态pass不证明后续代码修改文字、图片、显隐或事件就会生效。

默认序列化状态与有来源的运行展示状态分开。状态夹具要记录字段、来源与依赖，不改被验Prefab或硬编码业务答案；脚本禁用导致的空白、Null图形后端或均匀灰帧不能签视觉一致。缺展示依据的具体项记unverified，不阻断无关样本。跨版本画面差异按版本记录，不改旧数值/资产去匹配新截图。比较按[同页同状态同视口](../../grea/references/实际体验与画面对照.md#开发与ui对照)，容差事前明确。

第二阶段单独核脚本生命周期、事件、数据刷新、列表增减、动态布局/动画、真实输入及关闭重开；按[布局所有权](../../grea-develop/references/Unity界面还原与输入交互.md#布局属性所有权)排查写者。`dynamicAcceptance`与静态结果分列，未验或partial不抹去已证实的静态pass，也不升级整体恢复/游戏完成。服务缺失不能排除本地可验行为；有据响应形状只支撑对应展示，不证明交易/发奖。

仅批准双目标时分别验两个目标；固定引擎、依赖、producer及批准计划样本数，工具隔离验证不恢复暂停产品。源组件、闭包节点和核心样本各用自己的分母，多个状态不凑多个样本。原生操作核实际provider能力，缺能力不猜命令或自动装引擎；物理输入与回调夹具按[测试层级](../../grea/references/测试与结果交付.md)分别报告。必要负例检查缺字段/字体/材质/事件不会被当成功，修复进入monkey通用规则或可追溯输出，不依赖每样本外部补丁。

## 生成态、保存态与项目采用身份

| 阶段 | 身份和适用检查 |
| --- | --- |
| 源生成态 | 固定来源、工具版本/提交/producer、请求与生成manifest；原件只读，按生成清单核哈希，不覆盖旧清单 |
| 原生保存态 | 由同一候选导入、保存、独立重开形成的目标工程与原生回执；绑定前态、引擎版本、后态文件/meta哈希、实际GUID/localID及具体变化依据 |
| 项目适配态 | 明确所选子集、旧新路径/namespace/引用映射、既有资产复用与业务接线；保存原始候选及适配差异，采用后的原生回读绑定项目实际后态 |

Unity合法导入可改写.meta及版本文件，但“引擎会改文件”不是全量忽略规则。生成态审计发现差异时保留原失败；仅在固定provider确有保存态合同、前后链路和当前字节仍匹配时采用该层回执。不能以保存态回执证明生成态字节未变，也不能自行改manifest、按扩展名/数量批量豁免差异或把任意修改列入白名单。`provider_verified_editor_readback`只在实际支持它的入口与版本成立；直接CLI已有回执不等于GREA typed pipeline已支持那个版本。

选择性采用同时核资源引用依赖与C#编译依赖（基类、普通类型、程序集/包及同批脚本），GUID闭包不包含全部代码依赖。monkey声明来源/输出依赖，beaver负责采用闭包、导入/编译/稳定类型身份及事务验证；GREA只绑定两者固定合同。首次类型未加载导致引用差异时，不放宽校验或猜ID；由beaver交付可重复的分阶段操作及恢复边界，项目以固定候选复验。临时分阶段请求可保全进展，但不据此称通用采用器已修复。

交开发时保留原生静态、动态显示、输入和业务状态。采用成功后由项目修改文字/图片/进度/显隐并接线，若静态代理掩盖实时字段变化，恢复侧共因归monkey，采用时序归beaver，业务规则留项目。按[脚本接收与退役](../../grea/references/项目脚本沉淀与工具晋升.md#接收与退役)核实公开工具已替代通用临时实现；没有消费者实证，状态仍是未闭环。

## 开发接续

只有来源、候选与适用原生交接证据核清后，才由 beaver 在隔离工程采用/比较候选，由游戏 Agent 接续规则、界面、交互、服务和存档。这一步由操作者调用公开审计并按结果判断，工具不会自动拦截，见[当前实现边界](../../grea/references/monkey与beaver调用.md#当前实现边界)。已有工作工程参与比较/合并时，按来源身份保护既有代码、GUID、正式 JSON 和存档。此交接不是完整可玩验收；业务、视觉、真实输入、存档续玩和目标平台按开发阶段及本期范围另行验证。若交接不完整，保留缺口并停在恢复阶段，不以小样替代全量候选。

# 交付 · 游戏构建与版本发布

用于版本规划、开发构建、预览安装、归档、合并和Release发布。默认约定适用于新项目；既有项目先核对现行脚本、目录和用户约定，再迁移，不在一次普通修复中强制改名或版本体系。本页是此主题的权威入口，项目Docs记录实际配置与例外。

本次交付层级决定执行范围：开发预览做输入标识、构建及必要运行检查；安装、归档、正式发布只在本次要求覆盖时执行。不为了 Mac 预览走完整 Git/Release 流程。

新建项目先确定稳定游戏名，工作区 project-XX 只作索引；内部工程目录、Product Name、App/EXE 与进程名使用该名称，复刻优先原游戏名，重名加清楚区分词，不以 UnityProject 等占位名交付。已有目录改名先核对脚本、构建和存档影响。

未指定目标平台时默认 macOS .app；Windows、Android、iOS、微信小游戏等仅在用户明确要求时纳入。原版取证平台不自动成为构建目标。新项目窗口默认与实测见 [桌面显示](05-Unity-桌面窗口与显示适配.md#新项目窗口默认)。

## 1. 区分四种身份

| 身份 | 用途与规则 |
| --- | --- |
| 产品名 | Unity工程、Product Name、App/EXE及进程名使用稳定游戏名称，项目编号仅作工作区索引。 |
| 发布版本 releaseVersion | 用户可见的稳定版本，如v2026.10.08；发布后不可复用来表示不同内容。 |
| 构建ID buildId | 每次构建独立身份，建议UTC时间+短提交+平台/架构+唯一后缀；目录以创建失败拒绝重名，不覆盖旧产物。 |
| 源码/资产身份 sourceRevision | 完整提交哈希及输入状态；短哈希、分支名、产品窗口名不能单独证明制品来源。 |

Stage、Desktop、Refactor等内部阶段名可保留为历史别名，不作为用户寻找最终包的主入口。修复了源码不代表安装包已更新；更新current也不代表某个历史Release被修复。

## 2. 版本规划与分支

- 在项目现有计划维护版本目标：版本号、基线提交、目标平台/架构、本期内容、不包含内容、必需验收、存档兼容风险、阻塞及交付物。小修复不另造一套计划，阶段状态沿用[计划维护](../../../shared/01-流程-开发计划与进度管理.md)。
- 默认日历版本为`vYYYY.MM.DD`；同日第二次正式发布使用`vYYYY.MM.DD.1`、`.2`递增，不改写已发布版本。预发行可用`vYYYY.MM.DD-rc.1`；`rc.N`与正式版是不同标签。已有SemVer或渠道规则的项目沿用原体系，先声明同日热修及预发行约定。
- 开始一个明确命名的版本时，先服从当前会话与仓库分支约定；未另指定时从核实后的集成基线建立`codex/release-vYYYY.MM.DD`，小缺陷可用`codex/fix-<主题>`，有正式版本归属时在计划关联。未确定发布日期不要猜版本号，可先用主题分支和buildId。保留已有工作，不强制重置或重写历史。
- `main`作为已集成基线，不直接代表“已发布”。完成本期验证后按已有授权合并并推送；可快进则快进，需要PR/合并提交时遵守仓库规则。代码已在main时核对提交范围即可，不制造空合并。
- 发布版本确定后核对PlayerSettings/运行时版本显示和构建元数据。需要纯数字或单调递增版本的渠道，单独记录平台版本/构建号映射；不要将带v/日期的标签盲填进所有平台字段。产品标识、Bundle ID与存档路径保持稳定，除非迁移明确需要。
- 把版本号、渠道或资源写入Player后，它们就是构建输入。RC改正式版若改变这些输入，必须重建并复验；只有制品字节及嵌入身份本来就适用于正式版时，才可晋升同一包，并明确对应关系。

## 3. 输出目录

新项目默认使用项目根目录下的`Build`（与Unity工程的Assets/Library平级职责分离），名称大小写固定。所有任务产物留在对应project-XX内部。

```text
project-XX/
  <game-name>/                  Unity工程
  Build/
    README.md                   只指向current，说明当前版本/渠道/待验项
    current/                    唯一当前可交付入口；不存在时不得伪造
      README.md
      manifest.json
      macOS/<game-name>.app
      Windows-x64/              EXE、Data、DLL等整体保留
      packages/                 可分发压缩包
      reports/                  关联验收/构建报告
    builds/<buildId>/            不可原地覆盖的单次尝试
      build-info.json
      <platform>/               原始payload；失败时可能不存在
      packages/                 本次候选包（需要时）
      logs/
      reports/
  Archive/
    deliveries/<时间或buildId>/  被替换的current及原manifest
    releases/<releaseVersion>/  已发布快照或指向不可变制品的索引
  Evidence/                     截图、录屏、运行证据
  Analysis/                     原包分析与恢复材料
  Docs/                         项目计划、构建说明和验收
```

- 只创建已授权目标的平台目录；默认macOS不意味着自动生成Windows/Android/WebGL。其他平台采用同样的单次构建、清单和当前入口约定。
- 日志、失败报告、QA录屏不得散落Build顶层；QA会话证据归Evidence并由报告引用。运行时存档不写回Build或源码目录。
- 迁移旧output/Stage目录时，先清点调用方，保存旧→新映射；同步构建脚本、Editor缺省路径、安装/服务入口和活动文档。历史原始日志保留原路径并通过映射追溯，不批量改写证据。不能只改目录名却继续让工具创建旧目录。
- Build、Archive、原始证据、玩家/QA存档不进入源码Git；是否另行托管证据按项目约定。当前维护源码、必要工具、构建说明及依赖锁定信息须能独立克隆恢复。LFS资源必须实际拉取完成再验证。

## 4. 构建执行契约

1. **预检**：确认实际仓库/分支、用户改动、编辑器精确版本、平台模块、后端、架构、依赖和构建入口。复用当前CLI帮助与Unity工具路线；本规范不授权安装或切换额外平台。
2. **固定输入**：开发预览允许脏工作树，但记录dirty及可追踪差异；正式Release使用已提交且干净的源码/资产输入。版本文档可在构建后补充，须核对build提交到标签提交没有影响构建的变化。正式包不能只写HEAD而隐藏未提交修改。Release默认关闭Development Build；调试包标development，QA入口与正常运行隔离，不携带玩家/测试存档或默认自动测试行为。
3. **独立输出**：创建新buildId目录，拒绝将构建直接写入current、已发布目录或已有尝试。每次尝试保留成功/失败、命令参数、退出码和实际日志；不要预填成功或警告数。同一工作工程不要同时运行会改导入状态/平台设置的Unity构建。
4. **等待完成**：进程启动、日志出现或文件夹存在不是成功；核对退出码、BuildReport、错误及可执行payload。失败保持原current，后续重试用新buildId。
5. **必要验证**：跑受影响的规则/引用/存档检查，以及目标App真实入口、输入、声音和退出重开。平台未实机运行就记录not-run，不能自动改成verified；在用户已授权的交付范围内披露该限制，不凭一次跨平台构建宣称全面可玩。
6. **封装与校验**：macOS保留.app结构、可执行权限及实际签名状态；Windows保留完整依赖目录，不单发EXE冒充完整包。解包核对payload清单/哈希，去除Finder等无关缓存。单文件封装见下方 [运行身份](#单文件交付与运行身份)。

默认分发命名：`<game-name>-<releaseVersion>-<platform>-<arch>.zip`，例如`sample-game-v2026.10.08-macOS-arm64.zip`；通用包用已验证的universal，其他架构名称按实际构建填写。既有平台名已含架构（如Windows-x64）时不要重复。未发布预览以buildId命名，不能冒充正式版本。

### 单文件交付与运行身份

Windows 单 EXE 通常是自解压启动器，不是将所有 Unity 依赖编译成一个原生二进制。`package_windows_portable` 适用于已构建且存档位于外部用户目录的 payload：普通用户权限、私有临时目录、等待子游戏退出后清理。相对路径写存档的游戏不能直接套用；异常终止可能残留临时文件。工具不负责安装依赖，精确参数与失败边界见 [工具契约](../../../../docs/tools/制品与资源检查.md)。

分别核验构建成功、压缩格式、释放后逐文件 SHA-256 和目标系统实际运行。macOS 交叉构建与解包校验不能证明 Windows 可玩。Mono Player 的启动 EXE 可能跨源码修改保持不变，应使用完整 payload/包体身份及 buildId。只保留一个 dev App 的任务先安全退出旧进程，再核对新程序集/资源与启动时间；旧进程不能冒充已更新的包。

草稿 Release 必要时按 Release ID 回读，不把按标签 404 当上传丢失；源提交、输入状态和远端附件关系仍按本页各阶段确认。

### 安装程序与磁盘映像

仅在本次需要安装包时执行：从完整 payload 建立专用封装目录，排除 Unity 明确不应分发的调试备份、日志及测试存档，保留运行依赖。记录封装输入和排除项，不在唯一构建原件上直接删文件。

Windows 安装程序分别检查文件释放、快捷方式、卸载登记与卸载清单；卸载仅处理安装文件，玩家存档按约定保留。Mac 映像只读挂载后核对包体、权限与签名，并从交付入口启动回读存档和实际输入。解包哈希一致不能代替目标系统的安装、启动与卸载；ad-hoc 签名验证、发布签名和公证分别报告，单架构不称 Universal。

### 试玩视频交付

用户要求试玩或演示视频时，先固定录制 buildId、存档来源及覆盖路线；预留结算/返回时间，区分“入口展示”和“完整流程”。尽量先完成构建封装与录制器预检，再集中操作，避免并行打包造成大段菜单等待。

先录短片，检查目标窗口、画面比例、音轨与同步，按 [取证规范](../../grea-evidence/references/03-恢复-原版运行与内容取证.md#桌面窗口与权限中断) 限定采集范围。长录制按实际事件标记章节和问题时间点；结束后用媒体探测的实际时长、尺寸和音轨交付，检查全片解码并抽看关键段，不能用计划计时或录制命令成功替代。

录制清单与安装包清单分别标明构建和 QA 状态；二者不同则写明差异，不能用开发包视频证明普通包已实测。说明剪辑/变速情况、实际覆盖与未覆盖项，保留原片和已知缺陷。音轨有数据、听感正常、原版同状态音频一致仍是不同结论。相关工具先复用 `video_manifest`/`video_sheet`；固定窗口或项目路径的录制器未经泛化验证不纳入通用库存。

### 内容指纹、独立恢复与受限传输

内容指纹须声明相对路径正规化、排序、字段、序列化/编码协议及版本；清单文件本身的 SHA、内容集合 SHA、源码提交和包体 SHA 分开记录。不同协议得到不同摘要时逐路径/字节核对并登记映射，保留旧清单与原件，不覆盖历史值来制造一致。无 Git 历史的源码归档恢复后可建立新的干净本地检查点；新提交不是原来源提交，未变内容指纹仍可核对。归档字节回读不冒充新的冷导入或独立维护演练。

服务端附件限额导致完整包无法上传时，仅在本次交付允许且不扩大权限/可见性的前提下使用有序分片：记录片序、每片和合成整包的字节数/SHA，给出明确合成命令，下载全部片后按序合成核验；缺片或顺序错误不能当完整包。片大小和上传接口留项目，不设通用服务默认值。嵌入显示版本、buildId 与 Release 标签分别披露，复用原包不能悄改其版本身份。

进入发布新阶段时更新当前清单/剩余项，删除已完成发布步骤的过期“未发布/未推送”描述；原候选说明保留时间和原阶段，不将它重写成当时已发布。安装、current 晋升和未测平台不随 Release 成功自动关闭。

## 5. 清单与current晋升

清单至少能回答“哪个包、来自哪里、验证了什么、现在是否发布”：

| 字段 | 内容 |
| --- | --- |
| 身份 | productName、releaseVersion（未确定可空）、buildId、channel（development/rc/release） |
| 输入 | sourceRevision完整哈希、sourceDirty、实际构建时刻/时区、Unity版本、依赖锁定依据 |
| 平台 | platform、architecture、backend、developmentBuild、平台版本/构建号 |
| 结果 | 构建退出码/报告、errors/warnings、payload和压缩包SHA-256、相对入口 |
| 验收 | 各平台规则/运行验证状态、所用buildId、证据链接、已知缺口 |
| 发布 | 标签及解析后的提交、Release URL、远端附件核验结果；未发布时留空 |

字段可映射到既有JSON结构，不要求仅为改字段名重写工具；构建记录和多平台交付manifest可以分层。外发清单去掉本机用户名、绝对路径、完整命令中的敏感参数及存档内容。多平台包原则上来自同一输入提交；若某平台尚未更新，明确标旧版本或不纳入本轮current，不能夹带旧Windows包冒称同版修复。

晋升先在临时目录完成候选复制、验收状态和逐文件校验，再完整保留旧current及其清单后切换；切换失败能恢复旧入口。记录本期必需验收已通过及明确保留的范围外缺口，不把“显式晋升”变成重复向用户索取既有授权。README由manifest同步生成，避免手写两个不同的“最新版”。

current只表示最新审阅的交付候选，可能是尚未发布的修复版。releaseVersion与channel要如实反映；不得因为旧Release URL存在，就让新current显示已发布。

## 6. 安装、发布与回滚

- **安装验证**：运行前核对进程真实路径与完整payload身份；先安全退出匹配的旧应用，备份受影响存档，按平台正常应用位置安装。正常数据使用应用用户数据目录；QA使用显式隔离存档/命令通道。更新后核对版本、文件、启动状态及进度兼容，不以同名窗口或单个EXE哈希判断成功。
- **Git发布**：沿用会话已有提交/推送/发布授权，核对远端基线和标签是否存在。版本标签指向明确发布提交，main/分支/标签关系可回读；不强推改写已有正式标签。main与标签之后的新修复应规划新版本，旧发布不变。
- **Release附件**：可先用草稿完整上传已验证的平台包和SHA256SUMS，再回读附件名称、上传状态、大小与哈希后正式发布；服务端没有可信哈希时下载回读计算。版本说明列出变化、包的源码身份、各平台实际验收边界，以及 [许可证与再分发](09-交付-许可证与再分发.md#4-流程) 要求的许可证一节。源码自动压缩包不能替代游戏制品。
- **失败恢复**：网络EOF/超时属于结果不明，先查已有Release/附件再重试；不盲目重复创建或覆盖。上传完整但未正式发布、正式发布但附件缺失分别报告，任务有条件继续时完成剩余步骤。
- **归档与回滚**：发布快照不可变，保留标签、附件哈希和验收索引。回滚从明确旧清单恢复，重新验证存档兼容；遇单向迁移不能仅换旧App假装可逆。清理历史需项目保留策略及适用授权，不按文件年龄盲删current、发布快照、唯一失败证据或备份。

## 7. 收口与前向检查

交付说明只给一个当前入口，列版本/buildId、平台、是否已安装、源码提交/Release链接及确切待验项。版本计划、manifest、README和远端状态不一致时先纠正，不靠“最终版”“最新final2”等名称替代身份。

维护本规范时按 [grea 任务场景集](../../../../tests/scenarios/README.md) 核对预览范围、同日热修、多平台失败、已集成提交与构建输入变化；场景预期不在本页重复维护。

本规范描述可复用的输出组织与发布校验方法；具体版本命名、构建目录和交付平台以当前项目约定为准，历史项目的关卡、脚本和验收缺口不构成默认要求。

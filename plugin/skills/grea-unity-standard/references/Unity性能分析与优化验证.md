# Unity · 性能分析与优化验证

用于本技能适用工程中的加载慢、运行卡顿、动态分配、纹理内存与包体问题。先定位可测瓶颈，再做有边界的优化；不改变玩法、随机顺序、画质或目标FPS来制造性能提升。用户已指定30 FPS等目标时保持不变，不能把限帧本身视作缺陷。项目参数、原值和专用脚本留项目，技能只保留流程。

仅当用户要求性能优化、改动影响性能热点或已有采样指出风险时启动本页基准；普通 UI 修复、目录整理和文档维护不自动执行 N 轮测试。

## 1. 先冻结基线和测量口径

- 记录代码提交及未提交差异、资源清单/哈希、设备、编辑器/SDK版本、渠道宏、构建选项、分辨率、质量档、FPS、场景、存档、随机种子、输入序列和采样时长。连续多轮优化分别保留上一轮版本作为本轮before，不能混用最初基线。
- 优化前后各跑相同N轮，未指定时可先取5轮；预先定义预热、冷/热启动和异常样本处理方法，保留每轮原值与排除理由。5轮适合初步对照，不自动构成统计显著性；波动大时增加样本或改进实验条件。
- 基准期间不并行压图、导入、构建或其他重负载工作。需要不同编辑器测试时，在明确版本差异的隔离副本中统一前后版本；不顺带升级正式工程。测试存档、公司/产品标识与正常玩家数据隔离。
- 先核验夹具实际走到了目标场景和负载；检查旧自动测试、SessionState键、启动钩子是否抢占流程。记录活动对象峰值、生成/回收次数、完成量和剩余量；按影响范围对照事件/状态轨迹，只有汇总数量一致仍不足以证明完整行为等价。
- 分开测量完整启动及下载/解压/编译/SDK/登录/云存档/主页/进入关卡阶段，帧间隔中位数与P95、CPU/GPU耗时、累计分配、GC停顿、纹理/总内存和构建体积。先确认计数器有效；不把不支持接口返回的0当作零分配。

### 仪器校准、输入资格与正式结论

采样器、业务观察探针及实际载荷共同组成仪器身份；新增观察器即使未改 sampler 文件，也须重新确认 ON/control 扰动和只读边界。资格通过只表示所声明输入可用于后续分析，不自动生成产品性能通过；导出成功、计数器完整或同帧双读未改变已观察状态，不证明全部路径无扰动。

跨进程单调时钟不能直接相减；声明时间桥、漂移与不确定度。外部 RSS 等观察须覆盖完整预热/测量窗口，低频采样峰值不当瞬态峰值。核对实际业务负载、显示尺寸、刷新率、构建与仪器条件；不匹配时记录限制或重新登记实验，不能静默更改预算制造通过。具体热键、负载数、轮次与设备值留项目，按本次性能风险选取，不扩大普通开发验收。

## 2. 图片、字体和图集

先遍历文件与Unity实际导入资源：PNG/JPG/TGA/PSD等、ICO/SVG、内嵌字体纹理、生成图集及平台模板原始图片。结合场景、Resources、动态键、图集和构建报告区分游戏依赖、制作源、文档截图与示例，不能仅凭目录或“未引用”自动删除；依赖边界见[资产治理](Unity重构与资源迁移.md)。

对于移动端小型UI/小游戏，在不破坏批准画质的前提下采用以下候选策略；高清桌面、放大展示、特殊材质等另定标准：

| 类别 | 候选最长边 | 判断依据 |
| --- | --- | --- |
| 小图标、简单装饰、技能底纹 | 128 | 实际显示像素、DPI、边缘和九宫格需求 |
| 小角色、物件材质、中型插画组件 | 256 | 屏幕占比、UV利用率及放大需求 |
| 弹窗、横幅、Logo、较大装饰 | 512 | 文字可读性、描边及拉伸质量 |
| 全屏背景、大幅插画 | 1024 | 目标分辨率下的清晰度与内存代价 |

1. 超过256的图片逐项记录用途、当前/目标尺寸、合理性、依赖和处理结果；保持宽高比、不放大小图，优先选择视觉验收可接受的最小档位。以1024为此策略的默认上限，确需超过时写明原因、导入/运行尺寸和成本，不能静默遗漏。
2. PNG可用pngquant量化，记录工具版本、参数、处理前后字节及哈希；从可恢复的原始全色图生成，避免重复量化已压缩图。检查透明边缘、渐变、描边、文字和切片；不把PNG文件压缩率当作GPU内存或传输收益。法线、数值纹理、LUT和SDF不套用普通调色板压缩；纹理语义优先于扩展名。
3. 源图尺寸、Importer上限、平台格式和实际导入尺寸分开记录。分层PSD可保留制作源并限制导入尺寸；SVG的viewBox是逻辑坐标，核验实际栅格化输出。SDK原始浏览器图片按其消费方式处理，不强行当Unity Sprite导入。
4. 缩图通过Unity Sprite Data Provider同步处理切片矩形、边框、轮廓和适用的PPU，保留GUID和local fileID；对齐整数像素并检查切片未越界。重导入后加载实际引用，检查九宫格、世界尺寸、碰撞轮廓和画面。发现无效引用时对照原文件重导入，区分新增回归与历史缺陷。
5. 按同界面/同类型及共同加载生命周期合图集；明确内置或按需加载，避免无关界面被迫常驻。页尺寸限制1024时预留padding，核对实际页数、格式、读写性、重复收录和打包后尺寸。UGUI及CPU像素读取路径需验证旋转/紧密裁切兼容性；按纹理复用读取缓存，并明确释放生命周期。图集变小不自动证明Draw Call减少。
6. 字体使用原生成器重新排布，不能直接缩小SDF或位图字体像素而保留旧字形坐标。先尝试保持字符集合、采样字号、padding、材质和引用身份，校验缺字、fallback、静态/动态扩图及实际文本显示；装不下或画质不合格时记录例外或另定分图方案，不能为1024硬删字符。
7. 用清单和校验器约束源图、导入物、字体及图集页；生成/构建职责遵循项目资产写入契约和SpriteAtlas技能，不在普通构建中意外重写受保护资产。专项工具按当前可用的Sprite Editor、SpriteAtlas、TMP优化技能路由，项目专用清单和导入器不直接提升为通用工具。

## 3. 动态分配、场景搜索和首屏依赖

只在调用链与采样支持时采用以下做法，不能机械套用：

| 症状 | 优化方向 | 必须保留与验证 |
| --- | --- | --- |
| 高频Instantiate/Destroy | 按资源/材质等兼容键复用完整对象，设置容量和释放策略 | 重置变换、动画、回调、携带/目标状态；租期或版本号隔离旧异步回调；切关/中断回收；比较常驻内存代价 |
| 每次寻路/更新分配数组 | 按容量复用工作区和路径缓存 | 排序、同分次序、随机调用及update order不变；考虑回调重入；需长期保存的结果不能引用下一次会覆盖的临时数组 |
| 拾取时全场查找并猜测对象 | 由任务或事件显式传递执行者/归属，必要时维护生命周期受控索引 | 实际携带者、销毁/归还/切关、空目标及旧任务失效；不能只按“最近对象”替代业务身份 |
| 首屏串行等待 | 列出依赖图，让独立下载、引擎初始化与SDK工作并行；只准备首屏必需数据 | 不绕过账号/云存档核验；临时登录凭证只在内存中短期单次使用，失败/过期回退；记录重试、取消及旧回调隔离 |
| 主页提前建完整关卡 | 分离数据解析/预览和进入关卡时的实例化 | 新玩家、老存档、恢复云档、继续、切关、旧批绘/缓存清理；同时测主页和首次进入关卡，明确延后成本而非宣称成本消失 |

正确性回归覆盖正常完成、失败、中断、复用、重入和切关。池化和缓存可能增大常驻内存，必须同时报告收益和代价。组合优化只支持组合效果；要归因到某一改动，需专项对照或分阶段版本。

## 4. 复测、真实入口与交付

- 按冻结条件重跑N轮，列逐轮原值、中位数、尾部指标、绝对变化与百分比。明确中位数的计算层级和单位；无改善、退步、调度噪声及不支持计数器都如实记录。限帧下平均FPS持平时，不把资源变小改写成FPS提高。
- 同条件构建前后版本，分别报告源文件、Unity data、平台转换包和实际下载字节。冷/热缓存不同不能比较构建或启动耗时；源图片总量包含文档/示例时单列。Editor内存不等于设备RSS，未压缩data不等于CDN传输量。
- 在目标渠道启动实际制品，读取控制台、错误弹窗及网络日志，验证主页出现、真实点击开始、进入关卡和基础交互。**HTTP 200、资源下载、Editor回归、离屏截图或构建成功均不能单独证明可玩。**
- 普通浏览器与微信小游戏是不同运行环境：先检查渠道宏、模板、SDK初始化时序和平台API。需要浏览器预览时明确测试构建边界；不能直接提供微信渠道包后声称浏览器可玩，也不能把模拟登录或广告当作真实服务。修复模板还要检查SDK回调是否早于游戏实例赋值、失败/重试是否能退出等待。
- 真机加载/FPS结论必须有同设备、网络、缓存、温度/电源状态及相同游戏负载的前后记录。仅完成本地测量时，结论限定为本地，列出待验证项，不把用户原先的启动秒数与本机新结果直接相减。
- 交付一份项目报告：基线身份、改动及理由、逐文件策略/例外、N轮原值、构建结果、行为/视觉/真实入口验证、失败记录与剩余风险。原始日志、截图和测试副本留项目输出目录，摘要JSON和报告按项目规则纳管；提交或发布遵循当前授权。

# Unity · 重构与资源迁移

工具推荐：unity_asset_ledger snapshot/compare/check-plan、unity_dependency_audit及Unity Editor API。 入口和限制见 [工具清单](../../../shared/02-工具-选择与调用.md)。

适用于已能运行的恢复工程，需要拆职责、整理Assets、移除旧框架或建立持续开发入口时。先在项目落盘 [Unity 工程标准 v1](05-Unity-工程结构与开发规范.md) 与实际例外，冻结行为基线，再改变结构；不把项目目录搬家、文件改名或构建成功当作功能等价。用户明确授权的换皮/玩法改动另列版本目标，不混入“纯重构没有行为变化”的结论。

## 1. 开工先确认什么是真实工程

核对实际Git根、分支/提交、Assets/Packages/ProjectSettings、ProjectVersion、正在运行的Editor、局部说明及最新验收。Hub导入失败不一定是工程损坏：某些入口扫描所选目录的子工程，先看本次日志与官方CLI识别结果，不补造版本文件或先删除Library。

已有编辑器占用时使用已发现的Editor接口；不能控制或需要独立发布构建时，采用隔离工作树/副本，避免争用同一个Library。切分支前考虑活编辑器自动刷新；从旧布局跳到新布局可能触发大批重导入。暂存区、未提交修改、自动序列化配置变化分别检查，不丢掉用户工作。

冻结范围、基线资源/代码指纹、外部存储键、动态加载键、关键时序、现有验证与未决边界。格式化、改名、职责抽取、行为修复分批，避免一次混合到无法定位回归。计划更新沿用[状态维护](../../../shared/01-流程-开发计划与进度管理.md)，不再建立第二套进度入口。

## 2. 先画所有权，再拆文件

| 职责 | 应回答的问题 | 常见误区 |
| --- | --- | --- |
| Bootstrap | 谁创建依赖、解析启动配置、持有顶层生命周期？ | 业务模块自己寻找全局服务并重复初始化 |
| Domain/规则 | 哪些输入输出可独立验证，能否保留原oracle？ | 把引擎对象/UI组件嵌入纯规则测试 |
| Gameplay/会话 | 谁拥有状态、队列、槽位、目标预约和在途任务？ | partial拆成许多文件，却继续共享所有状态 |
| Services | 谁负责存档、奖励、音频及平台适配？ | UI回调直接改进度并保存，取消/失败遗漏回滚 |
| Presentation/UI | 谁只读状态、发出请求、管理视图和反馈？ | 表现组件直接判胜负、发奖或消耗资源 |
| QA | 验证从什么入口驱动，如何隔离存档与生产代码？ | 仅移动到Tests目录，生产仍能反射启动测试 |

这些是既有工程的职责盘点入口；选择标准化后，具体目录、程序集与组件契约以 [工程标准 v1 的程序集分层](05-Unity-程序集分层与生命周期.md#开发框架与依赖方向) 为准。按实际边界引入接口和asmdef；纯规则优先保持引擎无关，不为分层先建空壳或无需求的框架。适配partial可以作为阶段接入缝隙，但应注明其角色，不能当作已解耦的证明。

抽取模块时先记录调用顺序、状态归属、资源所有者及取消责任。重点检查：目标预约→扣弹→命中→移除→结算；合并时任务所有权转移；暂停/切关/销毁后的残留；提示/转场是否被玩法StopAllCoroutines误杀。保留原共享随机调用关系，同种子不保证不同帧时/时钟下的调用次数相同。

## 3. 建立可持续的内容与构建边界

原始证据、转换输入、生成基础资源、人工维护资源、QA证据和发布制品分开。只有运行或当前编辑必需内容进入Assets；备份、反编译资料、旧导入中间文件与历史一次性脚本放项目内部的独立目录。不能用移动到共用grea再做符号链接破坏项目自包含。

生成基础Prefab与人工Prefab Variant/覆盖层分离，Catalog引用正确的编辑层；明确重生成覆盖范围。活动内容默认按真实资产类型归类，Spine/字体保留完整资产组；详细类型表、供应方例外和动态 Resources 分布见 [标准工程目录](05-Unity-工程结构与开发规范.md)。只把原导出树改名为 Recovered/Original/Working 不满足“按类型整理”的要求。实际模块名按项目职责确定，不创建空壳。

将Import、Author/生成、Validate、Build、Package分开。普通Build不隐式重新转换原包或重建场景。预构建图集操作要符合该项目的资产写入契约；若普通构建要求Assets不变，就提前显式生成、构建只校验/打包缓存。实际比较构建前后资产指纹，不只依靠“不会写入”的代码注释。

旧工具退出时先查调用方：有合法调用则保留兼容或迁移；依赖旧布局的危险重建入口应明确失败并指向隔离基线，不留下“命令能运行却把旧目录全部建回来”的陷阱。日常文档替换为当前入口，历史证据注明适用提交，不把过期命令与现行命令并列混用。

## 4. Assets清理：从引用根审计到可核对清单

1. 定义根：构建场景、Catalog/配置、项目设置、预加载资源、编辑器生成输入、图集/Addressables等构建隐式入口。
2. 补动态引用：Resources/路径/名称查询、反射、Shader.Find、P/Invoke、平台插件、逻辑关卡映射。代码、asmdef和原生库不因缺少文本GUID边就删除。
3. 审计过时根：Catalog里“全目录加载”的旧项可能把废弃图集假装成活依赖。先按真实调用收敛根，再求闭包；经其他场景/配置反向引入旧Catalog时也要检查，不能仅按扫描结果清零。
4. 区分仍运行、仅编辑/生成需要、仅历史证据、待确认和可退休。102个文件、729个图标之类数量不能直接推导可玩关卡覆盖。
5. 产出逐项旧路径、目标路径、GUID、实际导入类型、理由、动态键/对象name契约、调用方更新和验证方式。未使用只是调查结论，不是删除授权；按当前会话范围执行，权限审查拒绝时提供具体清单，不拆批规避拒绝。

[依赖审计器](../../../../docs/tools/制品与资源检查.md#unity-导出依赖审计)只覆盖文本GUID闭包；[资产台账](../../../../docs/tools/制品与资源检查.md#unity-资产迁移台账与预检)记录身份及路径变化，二者都不证明资产可删除。

## 5. 命名、移动与可恢复执行

### 名称有多种身份

文件名、Unity对象name、GUID、子资源fileID、Prefab节点名、逻辑key、Shader/PInvoke符号和存档键不是一回事。以Prefab用途、状态页、动画帧和联系表为依据给哈希图片/字体起业务名；不能全局去掉Recovery前缀、后缀或把合法中文视作乱码。

关卡图标可改物理文件名而保留Catalog逻辑key。材质/动画/Mesh的对象name可能参与运行查找；重命名后在新Editor进程回读。Sprite切片或导入设置改变还需检查子资源fileID、UV、边距、pivot与引用，仅GUID相同不够。遇到大小写、Unicode规范化、目标重名或同名不同用途，先定义无歧义映射，不追加随机哈希糊弄命名。

### 推荐执行顺序

- 先验证清单对应当前路径、GUID及必要内容哈希，确保没有把过期审计应用到新工作树。
- 复制将退休的资源与.meta到Assets/Packages之外，逐文件验证；源文件与备份不同则停止，不能覆盖旧备份。便携恢复清单明确排除.DS_Store等缓存，不能依赖未纳入Git的文件。
- **先在Editor同步创建/登记目标父目录并完成需要保留GUID的目录移动，再暂停文件导入做批量文件移动。** 新文件夹尚未进入AssetDatabase时，MoveAsset会报父目录不可用；不要靠反复重跑整个删除脚本解决。
- 用AssetDatabase移动/重命名/删除，StartAssetEditing必须配finally StopAssetEditing。分阶段保存日志；异常不意味着此前操作全部撤销。
- 恢复时按GUID确定项处于旧路径、已审核中间路径还是目标路径，并重验备份。只继续未完成项；未知状态、目标已有内容或源已改变时停下调查，不“存在就跳过”。
- 根引用收敛且备份验证后再退休旧资源；最后清理真正空目录。被图集、Addressables或生成流程引用的目录不能因只含.meta而自动认定可删除。
- 新Editor回读GUID/子资源/名称契约、场景及Prefab引用，重新编译并按影响范围回归。普通构建检查资源未被意外改写。

Unity生成的YAML/meta可能含合法行尾空格；源码/文档格式检查与序列化输出检查分开，不为消除git diff --check提示手工重写场景/元数据、破坏已验证哈希。

## 6. 可编辑性与旧框架退役

分别登记：加密（有依据）、编码/混淆、压缩、发布二进制、正常编译产物、烘焙数据、缺少制作源。扩展名或“文本打开是乱码”不能证明加密；可读取/转换也不等于拥有原PSD、DCC、骨骼控制器或字体制作源。

旧UI迁移专项见[UI框架迁移](../../grea-native-port/references/05-Unity-UI框架迁移.md)。退役前确认运行引用、Editor/QA/生成/打包入口已替换；保留许可证、来源、GUID与哈希、恢复方式。仍被位图字体引用的原图集等像素资源可以继续使用，不能因文件夹叫fgui就一起删掉。

恢复说明应明确“在哪个基线/隔离副本恢复”，不能建议把旧适配源码直接叠加到新工程，造成同名类型、旧Catalog字段或生成路径冲突。

## 7. 验收、发布与状态交接

规则、GUID/对象引用、Editor编译、真实输入、视觉/音频、跨进程存档、性能及目标平台分别记录。脚本化内部调用通过不代表OS输入通过；同机不同随机轨迹只支持性能风险筛查，不证明改善比例或严格等价。

需要交付或发布时遵循 [构建输出与版本发布](../../grea-delivery/references/09-交付-游戏构建与版本发布.md)，本页不另定义源码、包体和远端身份。结构任务本身不自动进入正式发布。

收口还要检查：本轮工具留在项目、临时迁移脚本不参与生产编译、旧构建/导入命令无静默危险、当前文档与目录一致、未验收项仍可见、活工作树没有被丢弃的用户修改。

## 迁移结果与重跑工具

`unity_asset_ledger compare` 会把计划内移动也报告为变化；不要把退出 1 一律当失败或忽略。用 `verify-moves --before ... --after ... --plan ... --output ...` 核对计划内文件的 GUID、内容/meta 哈希与 Resources 相对键；再审查 compare 的目录增删和计划外变化。该只读检查不证明 Unity 类型、名称和子资源加载。

需要子资源与实际 Editor 类型证据时，使用 NativeExitEditorAudit 的 GUID/local fileID、Sprite 几何及对象依赖观察，再由 `unity_asset_ledger compare-editor` 对照前后报告。自动 Assets Resources 根排除 Editor 目录，Package Resources 与动态键仍显式传入。观察始终为 editor_observed；静态、Editor、实际 Player 和玩法验收分别记录。新配置或资源转换可使用显式有限候选工具，先在自有样本验证 schema、人工冲突、关闭重开、直接 Play 与删除转换器后的构建；不得把有限切片推定为全 Cocos 转换能力。调用边界见[制作链](../../../../docs/providers/unity-authoring.md)。

精确文件路径替换、可证明一致的目录前缀替换与动态拼接分别审查。迁移脚本本身、旧提交 git-show 路径、原包证据不能一起全局替换。重跑须按 GUID 核对原路径、显式过渡路径或目标路径，并拒绝占用目标；脚本编译失败后先修错误，不重复运行整个迁移。

类型整理的返工依据见 [历史来源（外部历史资料）](../../../../docs/工作区接入.md#外部经验和项目资料)。

# GREA · 调研、恢复、开发与发布

GREA 维护流程与判断，monkey 恢复原游戏为独立候选，beaver 执行开发工程操作；游戏业务与可玩结果由项目开发者负责。先核用户目标、实际工程、局部约定、版本和已有证据，再加载本次阶段。

## 五个入口

| 当前任务 | 技能 | 本阶段出口 |
| --- | --- | --- |
| 体验、分析品类/系统、评估成本与立项 | [grea-research](../grea-research/SKILL.md) | 有来源的调研结论、范围建议和未知项 |
| 取得技术证据、从包体恢复或跨引擎转换 | [grea-recover](../grea-recover/SKILL.md) | 来源去向清楚的独立候选与实际恢复缺口 |
| 采用工程、补业务、功能开发、换皮、Go服务、治理与修复 | [grea-develop](../grea-develop/SKILL.md) | 可维护工程、已实现功能和受影响验证 |
| 构建、候选验收、打包、版本说明及获准发布 | [grea-release](../grea-release/SKILL.md) | 身份一致的制品、校验与交付说明 |
| 维护GREA自身的Skill、调用合同或插件 | 本入口的维护参考（`maintain`） | 规范/接口修订、兼容检查与明确的本地验证 |

一般流程为调研 → 恢复 → 开发 → 发布。每个箭头都对应本次实际授权和交接条件，不是安装技能后的自动执行序列。已有工程或获准原创设计可直接进入开发；已有候选可直接交付；只读提取在恢复阶段的取证模式结束，不自动进入转换。发布发现缺陷回到开发，来源转换共因交 monkey。

换皮、Go 服务、Unity/Cocos 规范均是 `grea-develop` 的专题，不再单列技能。恢复按来源/目标选择参考，不把源引擎和目标引擎混同。旧模式如 `reskin`、`evolve`、`port`、`deliver` 仍是兼容工具参数；技能目录调整不改变工具 ID、CLI/MCP 输入接口或支持能力。

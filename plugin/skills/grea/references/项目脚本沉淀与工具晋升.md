# 维护 · 项目脚本沉淀与工具晋升

项目 `Tools/` 中的脚本何时留在项目、何时参数化、何时作为通用缺口归入 GREA 的功能模块。游戏规则、ID、账号、价格、服务配置和原件证据始终留在项目；可复用的实现和回归样例在 GREA 仓库单写。

## 判断顺序

1. **同项目复制两份以上、只差参数** → 在本次获准维护范围内合成一个脚本＋请求 JSON；旧编号副本在证据保留后退役，不再新增编号文件。
2. **不含游戏规则、ID 或账号，第二款游戏也会用到** → 作为通用缺口交给对应模块（见下表），附最小复现；项目暂用现有脚本，不因等待工具阻断业务。
3. **含游戏规则、数值、服务业务或私有身份** → 留在项目，自包含；不移出后改符号链接。
4. **只是一次性调查** → 结果写入证据，脚本可留历史但不进入日常入口清单。

最小复现必须包含：固定工具身份（版本/SHA）、命令与目标、预期与实际、错误位置、影响、可用替代。没有真实任务依赖或可操作证据，不开工具新版本。

每项通用改进还须绑定消费者任务、现有能力核查、固定交付、实际采用及结束条件，见[固定候选与运行连续性](固定候选与运行连续性.md#从缺口到结束)。先核现有spec/profile与公开操作，确有缺口才扩展；工具单测通过不算项目问题关闭，游戏无依赖部分继续推进。

## 通用能力的归属

| 工作内容 | 可查询的操作示例 | 项目保留 |
|---|---|---|
| 来源与依赖盘点 | `grea source inspect`、`grea source index-unity` | 原包和范围批准记录 |
| 纹理和方法恢复 | `grea asset acquire-unity-textures`、`grea code inventory-unity-methods` | 原规则断言、身份与证据 |
| 成组 Prefab 与增量接收 | `grea prefab recover`、`grea prefab intake-plan` | 选择清单与项目基线 |
| 工程采用与迁移 | `grea project adopt-plan`、`grea code csharp-rename-sequence` | 本项目迁移清单 |
| 界面接线与运行 | `grea ui wiring-plan`、`grea qa player-run` | 业务回调与实际运行验收 |
| 配置、协议、构建 | `grea config schema-validate`、`grea server protocol-tools`、`grea build payload-verify` | 字段语义、服务身份与数据 |

先用[命令参数索引](功能模块和命令参数.md)核实操作、输入和当前版本的限制。项目专用规则的验证见[规则与随机一致性](../../grea-develop/references/规则与随机一致性.md)。

## 接收与退役

接收方先冻结源脚本身份与许可、参数化并隔离验证，再由项目在自然安全点切换调用；切换核实后项目脚本退化为请求文件或薄调用。已固定旧链的在途版本不强制迁移，也不重导已完成的恢复结果。

通用脚本的退役依据是“真实缺陷→所属工具修复→固定版本/producer/合同→项目通过公开入口使用→原问题解除→重复调用仍成立”。项目维护一份旧脚本到新操作/请求的映射，关联固定锁、原失败与新回执；生成态、保存态与项目适配差异保留。依赖扫描、分阶段脚本导入、代理刷新等通用实现未被真实替代前不删除或假装退役；业务回调和本游戏数值仍留项目。工具单测、doctor或GREA方法修订不是消费者采用结果。只验证本次受影响路径，不为每个小改重跑完整恢复或全部工具。


已有工具 ID 可以转发到相同实现。切换时同时验证旧调用、新命令和实际消费者。

## 收口检查

- 本次新增脚本是否只是已有脚本的参数变体？
- 通用缺口是否已带最小复现交给接收方，且项目业务没有因此停住？
- 留在项目的脚本是否只含本游戏内容，并在项目入口文档登记？

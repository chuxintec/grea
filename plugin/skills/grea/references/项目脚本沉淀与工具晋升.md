# 维护 · 项目脚本沉淀与工具晋升

项目 `Tools/` 中的脚本何时留在项目、何时参数化、何时作为通用缺口交给 monkey 或 beaver。游戏规则、ID、账号、价格、服务配置和原件证据始终留在项目；GREA 只维护判断方法，不接收执行实现。

## 判断顺序

1. **同项目复制两份以上、只差参数** → 在本次获准维护范围内合成一个脚本＋请求 JSON；旧编号副本在证据保留后退役，不再新增编号文件。
2. **不含游戏规则、ID 或账号，第二款游戏也会用到** → 作为通用缺口交给对应模块（见下表），附最小复现；项目暂用现有脚本，不因等待工具阻断业务。
3. **含游戏规则、数值、服务业务或私有身份** → 留在项目，自包含；不移出后改符号链接。
4. **只是一次性调查** → 结果写入证据，脚本可留历史但不进入日常入口清单。

最小复现必须包含：固定工具身份（版本/SHA）、命令与目标、预期与实际、错误位置、影响、可用替代。没有真实任务依赖或可操作证据，不开工具新版本。

## 接收方：按发生阶段

| 项目脚本族（实例） | 接收方向与能力线索 | 留在项目的部分 |
| --- | --- | --- |
| 原包解码、原配置/BON/textconfig 读取、Wasm/IL2CPP 方法索引与反编译、原资源提取（`extract_original_*`、`decode_*`、`index_wasm`、`map_wasm_methods`） | monkey：来源 profile、批量导出、代码证据与配置解码 | 原规则含义的人工判定与证据台账 |
| 输入冻结、远程资源获取、全量交接（`freeze_inputs`、`acquire_resources`、`prepare_bulk_handoff`） | monkey：input-set、远程清单获取、bulk handoff | 获准范围与来源回执 |
| 候选采用、三方合并、迁移映射（`adopt_frozen_monkey_bulk`、`build_monkey_merge_map`、`adopt_verified_candidate`） | beaver：`adoption.plan/apply/rollback` | 业务选择与保留清单 |
| 资源移动、路径消费者、类型/namespace 重命名（`prepare/run/verify_standard_asset_moves`、`StandardTypeRename.cs`） | beaver：`unity.assets.move`、`references`、`csharp.rename-sequence` | 本项目迁移清单 |
| 原生 UI/Prefab 生成与编号构建（`build_native_*`、`prepare_native_*`） | beaver：`production.plan/apply`、`unity.ui.create`、`unity.prefab.edit` | 声明式请求 JSON 与业务回调 |
| 启动 Editor/Player 跑一个场景（`launch_native_*`、`run_editor_window*`） | beaver：`debug.start/target/tail/screenshot`、`player.run`、`batch.*` | 场景名、角色与验收判定 |
| 配置转换与读取器生成（`convert_fp_*`、`generate_*_reader`） | beaver：`config3.validate/generate/compare` | 字段映射与业务校验 |
| 服务栈升级、迁移、证书与协议（`upgrade_*_stack`、`verify_*_upgrade` 通用部分、`generate_server_protocol`） | beaver：`server.compose-plan/migration-*/protocol-tools/runtime-inspect` | 业务迁移断言、共享栈身份与数据卷 |
| 制品与包体核对 | beaver：`payload.verify`、`unity.build.macos` | 启动器与版本标签 |
| 主线逐日试玩与规则检查（`play_day*`、`check_*`） | 项目自有；方法见 [规则与随机一致性](../../grea-develop/references/规则与随机一致性.md) | 全部 |

表中名称是核对线索，并非GREA已适配操作清单；尤其服务运行/迁移操作须核实际合同，不能据表执行。能力名以当前 `beaver capabilities` / `monkey capabilities --json` 为准；表中能力不存在或状态不是 implemented 时，按缺口提交，不在 GREA 或项目里另建第二套实现。

## 接收与退役

接收方先冻结源脚本身份与许可、参数化并隔离验证，再由项目在自然安全点切换调用；切换核实后项目脚本退化为请求文件或薄调用。已固定旧链的在途版本不强制迁移，也不重导已完成的恢复结果。

GREA 旧执行工具遵循同一规则：在 registry（GREA 安装目录 `registry.json`） 中标注接收方和对应能力，接收方验收前保留原实现与工具 ID，不返回空成功。

## 收口检查

- 本次新增脚本是否只是已有脚本的参数变体？
- 通用缺口是否已带最小复现交给接收方，且项目业务没有因此停住？
- 留在项目的脚本是否只含本游戏内容，并在项目入口文档登记？

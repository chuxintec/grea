# 流程 · 开发计划与进度管理

工具推荐：复用项目状态文件及已生成报告；不为更新状态重复运行未变化测试。 入口和限制见 [工具清单](工具选择与调用.md)。

适用于跨阶段开发、重构、恢复项目及已有计划的续做。小修复在现有计划或验收条目中更新即可，不要求另建版本文档，也不固定使用 S0–S6 七个阶段。

版本目标、命名、分支和制品身份按 [构建输出与版本发布](../../grea-delivery/references/游戏构建与版本发布.md) 维护；本页只定义计划状态与证据更新，避免另一份独立版本进度表。

## 一份当前计划，分开进度与证据

优先维护项目已有计划。计划至少说明本期目标与范围、基线/开发分支（适用时）、稳定的阶段编号、实施内容、完成门槛，以及以下当前状态表：

| 阶段 | 状态 | 已交付结果及证据 | 剩余项/下一步 |
| --- | --- | --- | --- |
| S1：阶段名称 | 待验收 | 实现入口；验收记录的具体章节或报告 | 尚未执行的真实输入检查 |

- 阶段表是阶段状态的唯一权威位置；正文定义实施内容与门槛，标题不重复维护“已完成”。README、状态页和交接记录链接到它，避免多份独立进度表。
- 部分完成的阶段拆成可核验的任务。`[x]` 表示该任务自身完成门槛已达到；实现与验收是两项时分开勾选，不能用一个勾同时代表二者。阶段状态由本期必需任务及门槛决定，不按勾选比例自动判定。
- 验收记录承载规则、运行、原版对照等详细结果；计划链接到具体结论和证据，不复制整份日志。证据只在本地时注明位置与可用范围。
- 写明最近核对日期和适用代码/构建版本。复用历史记录时注明“依据已有记录核对，未重跑”，不把核对日期伪装成完成日期。

## 进度与验收维度的映射

本页状态只表示工作推进；[验收参考](测试与结果交付.md#单一验收入口) 的规则、运行、体验、身份、性能和平台结果表示证据，不与阶段状态混成一个字段。已接入只是实现里程碑。

例如本期要求规则、Mac 真实输入与原版视觉：前两项通过、视觉未运行时为待验收；视觉失败且要修代码时回到进行中。用户未要求 Windows 可标不适用并写范围理由，已要求但无目标系统则标未运行，相关任务注明阻塞条件。只有全部本期必需门槛通过才已完成；不得因通过项更多就忽略失败项。

## 立项前提与进度度量

- 恢复/复刻类项目开工前确认两个前提：素材与代码的使用授权范围，以及目标发布平台（小游戏、原生 App、桌面）。平台决定引擎、包体和性能路线；未回答时记为明确的阻塞或待定项并写明谁在何时回答，不默认“完全复刻”。
- 先冻结最小可玩闭环（正常入口→核心操作→首个经济循环→退出重开），外围内容只在闭环通过后扩展。大规模数据（数千订单/剧情行）用机制覆盖率＋抽样对照＋数据驱动验收，不承诺逐条人工核对。
- 进度只按正常入口的真实结果计算。直接调用业务接口、注入道具/游标/时间推进出的状态是调试数据，不是可玩进度。
- 流程开销设上限：项目 AGENTS 只保留当前有效约束（约一页），授权溯源移归档；PLAN 顶部只写当前目标、断点和下一步，历史移到 history；不为每次集成生成独立 manifest。重复脚本、工作树和分支同样计入开销，见[项目脚本沉淀与工具晋升](项目脚本沉淀与工具晋升.md)。
- 并行工作树设上限（约10），删除前用 `git cherry` 等确认补丁已在主线且无未提交成果；用 merge/rebase 集成，不长期依赖逐提交 cherry-pick。

## 状态含义

| 状态 | 使用条件 |
| --- | --- |
| 未开始 | 尚未启动该阶段 |
| 进行中 | 已开始，仍有实现或修复任务 |
| 待验收 | 实现已交付，但必要检查未执行或证据不足 |
| 阻塞 | 有具体障碍使该项无法继续；写清原因、影响和解除条件 |
| 已完成 | 本期必需任务及明确完成门槛均有对应证据，未决缺口没有被隐藏 |

阶段部分完成时，在剩余项中列出具体任务。失败或新增缺陷使旧完成结论失效时，退回“进行中”或“待验收”，说明被替代结论及依据。保留历史证据，不仅在末尾追加日志。

发布/合并尚待用户指令时标注“待指令”；范围外或经用户同意延期的事项单列，不冒充完成，也不把未授权发布误写成技术阻塞。不得为了勾完清单自行删除必验项或降低门槛。

## 必须更新的时点

1. 开始或恢复工作：核对实际分支、代码与最新记录，选定当前阶段；发现过期状态先纠正。
2. 任务实现、接入、验收结果发生变化：在同一工作批次更新当前条目、必要勾选、证据与下一步；实现结束但未验证就写“待验收”。不要等整个版本结束才补写。
3. 失败、阻塞解除、范围变更或用户反馈推翻结论：同步修正当前状态和剩余项，保留变更原因。
4. 进入下一阶段、提交、交接或最终汇报前：核对下列检查单；文档更新与对应代码尽量同批提交。提交前不能预填尚未生成的提交哈希，已有证据注明实际适用版本。

不要求每行代码或每次工具调用写日志；以可复查的工作批次为单位。并行工作（已获授权时）由集成负责人核对证据后更新总表，子任务自报完成不自动等于阶段验收通过。

## 收口检查单

- 当前阶段状态是否与实际实现、接入和验收一致？是否存在“正文已通过、顶部仍待办”或反向矛盾？
- 每个完成项是否有对应结果和证据？构建成功是否被误当成实机或原版一致性通过？
- 所有未完成项是否仍可见，并写清下一步或解除条件？发布权限与开发验收是否区分？
- 摘要、任务勾选、验收结论和对用户的汇报是否一致？证据是否对应本次代码/构建，旧结论是否已标注替代关系？

只检查本次变化及其影响范围；文档整理不要求重跑未变化的游戏测试，也不能声称已经重跑。工具可检查链接、必填字段和格式，但不得根据测试数量或关键词自动升级为“已完成”。

## 成组开发与证据复用

代表切片确认后，按共享依赖成组推进：组内做受影响定向检查，在集成点集中验证，避免每个小改动都重跑整库/双端构建；也不能先堆完整项目再验证。依据实际 diff、输入与调用链选择复用范围：

| 变化 | 必要动作 |
| --- | --- |
| 仅审计器/政策变，产品字节未变 | 用新审计器重审固定原件，保留旧失败与审计器身份；不为更新结论重建产品 |
| 运行时、制作源或依赖变 | 重验受影响规则/入口、实际消费者及目标平台，不借用旧候选的相同文件名 |
| 仅文档、归档或传输变 | 回读链接、输入身份、字节和当前状态，不自动重跑游戏 |
| 影响尚不明确 | 先查差异与依赖；不默认复用，也不默认全套重做 |

失败停止依赖它的后续步骤，其他无依赖开发继续；只有真实共享资源冲突才协调窗口，不给所有任务新增审批。用户批准限定结项时更新该范围和剩余项，未验仍保持原状态；一次范围变更不能复制为无设备、性能不匹配或许可未知时的通用豁免。

# 流程 · 已恢复工程的有限二次开发

适用前提是已有可维护的恢复工程与明确二次开发授权。不是首次恢复、无限制原创或一键变体生成。先固定来源提交/制品与原待验范围，独立分支或副本、产品名、存档命名空间和构建输出；原工程、玩家档和已交付包不变。身份声明不是实际存档隔离证明，进入运行前由产品回读。

## UI/UE 变更与玩法不变量

旧v1 `evolve/ui_ux`保持本节约束；新v2及feature/tuning/prototype入口先读[生命周期合同](生命周期与变更合同.md)，按显式批准增量定义规则与兼容。本节以下视觉预算/不变量不自动限制已批准的新规则。用 `change-contract.schema.json` 声明基线**文件**摘要、源/新产品与存档身份、候选或批准设计文件参考与SHA、允许维度及玩法不变量。基线文件可为固定源码/制品清单或归档，其文件SHA不是源码集合指纹。`plan-workflow` 未提供合同时返回下一决策，Case/revision 必须绑定合同及对应基线文件摘要；它不替用户授权。

允许变化为视觉、布局、导航、反馈、可读性。关卡进度、战斗规则、伤害/碰撞/命中时点、RNG和选择池、费用/奖励/资格、持久化语义及动画事件/取消关系不变。不具备某类机制的项目在设计文件说明不适用，保持不存在的状态，不因此新增战斗/奖励系统或测试。产品另有玩法变更要求时先另定范围，不能套用当前工具与未变声明。约定整体UI/操作流程的比例只作页面/流程清单说明，不变成每页配额、像素比例、代码行数或精密百分比工具。

## 换皮主线的调优后置

以完整功能工程为换皮起点时，先按 [换皮制作](../../grea-reskin/references/游戏换皮与资源制作.md) 完成 S1 风格选样 → S2 UI/ICON/原画及所需 Spine 成套生产 → S3 选样100%原功能替换 → S4 用户确认样板风格后的全量换皮及Bug修复 → S5 游戏调优。前四阶段保留原布局、入口和操作；既有可玩候选不作为风格批准。约30%等UI/UE预算只约束最后的调优，不是美术覆盖率。独立UI/UE任务仍沿其本期授权，不强加美术生产。

需要机器表达此顺序时，在现有合同增加可选 `art_production`：`stage` 为 `style_sample/art_production/sample_replace/full_reskin/game_tuning`，`ledger` 绑定同一持续维护台账文件的当前SHA。前四阶段 `allowed_changes` 只含 `visual_style`；S4/S5要求设计状态为approved，S5还要 `reskin_complete` 绑定全量换皮与Bug修复完成回执。以上都是调用者声明，不是工具自动批准/实测。旧无此字段的有界合同保持兼容，不能把这种兼容当成绕过项目约定。

台账链接界面/角色/怪物/特效/关卡设定，并贯穿各阶段更新资源身份、设计版本、源稿、切片、Spine制作/导出、目标引用和状态。源/新产品存档隔离仍需实际回读；不为样板重新做全部历史待验、双端全量或长稳测试。设计等待时继续独立工作，费用工具、上传和安装按实际授权。

`theme_assets` 先 validate/preview，再生成新增、不覆盖的增量包。单Sprite PNG只允许保持画布与既有meta；GUID/local fileID、pivot/九宫格/PPU由Editor伴随工具实读。新增组件、布局或导航继续通过工程已有Unity API制作，不让主题工具写Prefab/Scene YAML。多Sprite、骨骼图集/附件、AnimationClip事件或改变画布均另行制作和验证，首版工具拒绝自动替换。

## 验收与交付

规则与持久化对照冻结旧基线；视觉/允许的UI流程对照批准新设计；候选设计可以做样板，但不能记录成批准美术通过。Case 的 rules 需要旧基线静态证据与专项测试，visual 需要批准设计与候选运行；源引擎残留整改按实际来源保留适用native维度。来源、角色、审批与实测仍是声明/证据的不同层。

只验证受影响入口、取消、返回、奖励和存档等实际风险，不把原待验改成通过。`grea-unity-standard`维护原生引用与生命周期；`grea-delivery`固定衍生产品/来源/构建身份，发布、推送和全局安装不由本模式自动授权。完整工具合同见 [主题映射](../../grea/references/providers/theme-assets.md)。

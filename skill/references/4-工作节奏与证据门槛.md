# 防返工与执行节奏

本页管理单次调查、代表闭环和跨模块接入节奏；完整恢复阶段由 [开发顺序](3-开发顺序与复用.md) 定义，证据与完成判据由 [验收](8-验收与协作.md) 定义。按本期影响范围选择检查，不重新启动完整恢复。

工具推荐：先复用registry中的命令契约；重复失败用有界测试与首差异报告，避免再次全量发现。 入口和限制见 [工具清单](9-工具目录与准入.md)。

在开始新模块、扩展相似页面、跨模块接入、调查停滞或出现集成积压时读取。与主 Skill 的恢复流程配合，不另建一套审批流程。普通小修复只执行受影响的检查；已确认且未变化的依据直接复用。

## 1. 实现前检查依据是否充分

先在已有验收记录或任务说明中用几行回答：

- 当前要恢复哪个原版对象、入口和运行状态？有没有排除同名但不同用途的候选？
- 图片、字体、布局与效果由哪些组件/资源引用确定？哪些来自运行代码？
- 关键未知项是什么？若猜错，会局部返修还是推翻整个页面/流程？
- 实现从哪个实际入口接入，以什么可观察结果验收？

据此选择动作：

| 情况 | 动作 |
| --- | --- |
| 关键结构与行为已有证据 | 实现，并验证动态状态 |
| 未知项仅影响局部 | 完成有依据的部分，将未知项隔离并标明边界 |
| 根对象、主要布局或核心规则仍靠猜测 | 暂缓依赖它的批量实现，先做定向调查或最小验证 |

不要求等所有字段完全解析才写代码；也不能把关键未知项变成自拟默认值并扩散到多处。依赖模块尚未就绪时可以约定接口，但不能把模拟数据验证称为真实接入。

### 完整流程与调度检查

适用于结算过长、阶段缺失、连锁顺序错误、组合道具或动画同步问题。先区分流程、状态调度和渲染问题，再决定改参数还是改结构。

1. **取得完整原生样本。** 从触发前录到流程完成、下一界面可操作；检查录像是否截断。片段只用于它实际覆盖的阶段。用户提供的原版观察应列为优先核对项，未重验前标明来源，不直接写成已实测结论。
2. **列出阶段与边界。** 在项目现有记录中使用下表，按事件对齐原版与复刻。区分庆祝横幅、HUD提示、结算弹窗等同名或同文案对象，不能因都显示某句文字而认定是同一阶段。阶段顺序以该游戏证据为准，不把某次项目的顺序固定为通用模板。
3. **追踪调用上下文。** 沿调用者、协程/更新循环、启停开关、完成回调恢复控制流。某个分支允许再次触发，只证明其可能性，不能证明整段持续时间、触发频率或必然执行；诊断日志阈值也不能直接当超时退出条件。
4. **核对状态推进方式。** 检查原版是否边运行边扫描，而复刻是否预先算完整局面再串行播放。后者可能拿未来棋盘作当前判断，并累加原本可重叠的等待。若此差异影响行为，先建立与原版依赖关系一致的调度，再校准速度；禁止用无依据的轮数上限、关闭连锁或整体加速掩盖差异。
5. **在真实入口验证。** 先验证一个完整代表流程，再扩展依赖同一调度的关卡与页面。原生样本不完整时可继续做证据充分的局部修复，但该流程保持待验收。

| 阶段/原版对象 | 触发与结束条件 | 原生起止时间/帧 | 复刻起止时间/帧 | 重叠、输入/跳过行为 | 资源/代码依据及差异 |
| --- | --- | --- | --- | --- | --- |
| 实际观察的阶段 | 包括完成回调 | 相对同一触发事件 | 相对同一触发事件 | 未确认则标未知 | 不用文件名代替观察 |

调度实现重点检查：道具身份随移动保留，生成、命中、开始下落、落地、稳定和销毁分别计时；候选扫描与全局空闲检测的先后遵循原版。逻辑和表现使用可对应的时钟，等待后不回退到计划时刻，也不把播放时间重复计入等待。重叠操作不能截断无关轨迹，结束条件须覆盖尚未完成的必要操作。

多部件动画先恢复原版启动关系。确需同步启动的图片、曲线、音效和粒子在准备完成后按同一时间基准播放，避免各自加载后自行起跑；异步旧结果在关闭或重入后不得重新挂回界面。按风险检查慢加载、帧率变化、暂停恢复和中断清理，不为不相关的小改动扩大回归范围。

## 2. 先处理可能推翻方案的风险

优先验证高影响且不确定的依赖，例如资源包能否在已有权限内取得、坐标/材质能否映射、动态布局是否由服务端数据驱动、核心效果在目标运行时是否可呈现。

每次验证明确“要回答的问题”和“结果会改变什么决定”。只有结果会影响实现方向或验收时才增加调查。首次内容获取与资源恢复按用户要求做全面盘点和可提取内容导出；功能修复阶段按具体缺口检索，不重复全包扫描、无目标人工反编译所有方法或提前完善范围外系统。

若缺少关键资源且当前访问路线不可用，记录具体缺口和对本期交付的影响；选择有依据的替代路线或先完成无依赖工作。暂存阻塞项不等于将它标为完成，也不等于擅自删减用户范围。

## 3. 一个代表性页面或流程先通过

在复用同一种布局、字体、切片、遮罩或动画方案前，选择能暴露这些风险的一个代表性页面，走通“原版依据 → 实现 → 实际入口 → 运行对照”。

至少覆盖一个实际动态状态，例如内容变化、展开、切换、关闭或重新进入。确认共用映射正确后再批量扩展。其他页面有不同 Camera、布局组件或运行逻辑时，单独验证差异，不能把首个页面通过当作全部通过。

优先复用已有且真正验收通过的页面，不为遵循此规则重新制作样板。

## 4. 调查检查点与退出条件

开始一轮非平凡调查前，写明当前假设、最窄检索对象、预期新增证据，以及何时复盘。根据调查成本使用少量尝试或一个短工作时段，不强制统一时长。

到达检查点，或连续尝试未新增有效证据时：

1. 汇总已证实、已排除及仍未知的内容。
2. 判断瓶颈是对象选错、工具/类型树限制、运行数据缺失还是访问限制。
3. 选择一次有新依据的路线切换；若没有新线索，暂存并转向可独立完成的工作。
4. 说明恢复调查需要什么新证据或条件，以及未解决会影响哪项验收。

除非输入、工具能力或假设有变化，不重复同一失败调用。不要只换工具名称重复同一路线。不得通过扩大访问范围规避权限限制。仅在用户的答案确实会改变范围、授权或产品取舍时提问；日常调查和路线切换自行处理。

## 5. 跨模块契约先约定

在已有代码接口或交接记录中写清本次真正涉及的约定，不创建形式化空文档：

| 约定 | 需要明确的内容 |
| --- | --- |
| 状态归属 | 谁写进度/奖励，谁只读；重复触发如何处理 |
| 坐标和时间 | 像素或世界单位、原点、轴向、缩放责任、毫秒或秒、暂停时钟 |
| 事件顺序 | 命中、伤害、消除、回填、结束回调的关系 |
| 资源就绪 | 加载完成条件、失败反馈、异步结果过期后如何丢弃 |
| 生命周期 | 谁创建、暂停、取消、销毁；关闭后是否仍有回调 |
| 集成归属 | 调用入口、参数/返回结果、由谁接入和验收 |

先接最小真实调用确认契约，再扩展效果。契约变更检查已有调用方，不能只修改提供方。避免多个模块各自换算同一坐标、各自发奖或各自管理同一效果结束状态。

## 6. 控制待集成数量

每项工作明确谁接入、谁验收及其依赖；没有可用接入方时，不继续制造大量独立模块。进度用 [状态维护](16-开发计划与状态维护.md) 的状态；接入情况另列实现里程碑，不另建一套状态枚举。

若主执行者持续消化不了已交付模块，或新工作依赖尚未验收的公共方案，暂停扩展同类任务，先清理积压。增加并发前确认有独立工作、明确文件边界以及足够验收能力。多 Agent 授权和交接规则见 [验收与协作](8-验收与协作.md)。

集成检查失败时，返修单说明原版期望、实际差异、证据和受影响入口；负责模块的执行者补齐问题，主执行者做跨模块复核，避免所有收尾都堆到一个人。

## 7. 固定对照条件并保留决策依据

原版与复刻的版本、显示比例、关卡/区域、进度、入口、语言和功能状态应可比。不同随机轨迹只比较适合比较的规则与效果，不要求无依据的逐棋子一致。动态效果对齐到同一事件，例如命中或回填开始，而非仅按请求截图的等待时间比较。

在项目已有验收记录中只保存会影响后续工作的决策，可用一行表达：

> 决定 / 依据与适用范围 / 已否定路线及原因 / 重新考虑所需的新证据

截图文件名不作证据结论；报告纠错后标明替代依据。交接时读取这些决策，避免重新采用已排除的根对象、资源或规则。临时方案保留边界，不能随着多次交接变成“原版事实”。

## 8. 用验收结果报告进度

阶段汇报回答：本阶段哪个用户可见流程已通过；还有哪些具体差异或阻塞；下一步要消除哪个不确定性。分别标识依据恢复、代码接入和实际验收状态。

只有对安排工作有帮助时才报告百分比；它不能直接推算剩余时间。调查、开发、集成和返工耗时有可核对记录时再分析效率，不从 Agent 数量或文件数量推断加速比。
